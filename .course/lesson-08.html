Lesson 08 · Week 2 · Day 8 · Native Device Monitor course

Shared ViewModels

~2 h · +0.5 h per extra UI track Milestone: m03 shell driven by a shared ViewModel Prereq: 07
Why this matters: the Device Monitor's real work (scanning, holding a connection, streaming sensor values) must not die when the user rotates the phone or opens another screen. It should also be written once, not twice. In m02 the scan lived inside the screen, and Android rotation cancelled it (Lesson 07, section 5). Today the scan moves into a ViewModel in shared Kotlin, and both apps only observe it. That's milestone m03, and it's the shape of every screen in the team's app: a shared ViewModel with a thin native UI on each platform. The ViewModel still builds its own fake scanner today. Lesson 10 shows why that's a problem and fixes it, and from Lesson 13 the scanner is a real radio.

Primary source Android's UI layer guide: UI state, state holders, unidirectional data flow and StateFlow, all in one page. Read it after section 2. iOS learners add Android's KMP ViewModel page before section 5: it's where the iOS owner comes from.

Tracks The ViewModel and everything in shared/ is the same on every track. Each track only changes how it observes the ViewModel: Compose and XML in section 4, SwiftUI and UIKit in section 5. Each excerpt shows only the lines its notes explain, and the complete files are in Full files at the end.

1. Move the work out of the screen

A screen is the wrong owner for long-running work, because the platform destroys screens whenever it likes. Android recreates the Activity on rotation. Both platforms tear down screens you navigate away from. A ViewModel is an object whose lifetime is the screen's logical life rather than its views'. Android defines it as "a business logic or screen level state holder", whose "principal advantage is that it caches state and persists it through configuration changes" (ViewModel overview).

The toy below runs the scan both ways. Start a scan, then rotate or leave the screen while it's still running, and watch both logs.

Tap Scan, then rotate while it scans. Why does the m02 phone fall back to "Tap Scan to look for devices."?

The scan ran in the screen's coroutine scope, which is cancelled when the Activity is destroyed. Saved values do come back, but only the ones written down, and a running scan can't be written down.

Leave the screen during a scan. What stops the m03 scan?

Stopping observation stops nothing: the UI also stops collecting when you rotate, and the scan carries on. Work stops when its scope is cancelled, and viewModelScope is cancelled when the ViewModel is cleared. Tick the iOS checkbox and leave again to see what happens when nobody clears it.

When does a ViewModel get cleared? "A ViewModel remains in memory until the ViewModelStoreOwner to which it is scoped disappears": an Activity that finishes, a navigation entry "removed from the back stack", a composable that "exits the Composition" (same page). Any coroutine launched in viewModelScope "is automatically canceled if the ViewModel is cleared" (Kotlin coroutines with lifecycle-aware components). The ViewModel class is multiplatform since AndroidX Lifecycle 2.8 (KMP ViewModel), so it can live in commonMain and serve both apps.

2. Design the UI state first

Android's guide defines it in one line: "if the UI is what the user sees, the UI state is what the app says they should see." Make it immutable, because "immutable objects provide guarantees regarding the state of the application at an instant in time". Expose it from the ViewModel "in an observable data holder like StateFlow". The UI sends events up and gets state back: "the state flows down and the events flow up" (UI layer).

  • Shared ViewModel (Lesson 10 calls it an inbound adapter)
  • Android
  • iOS

Make impossible states impossible. m02 described a scan with two independent variables. Two variables give four combinations, and one of them means nothing:

isScanningdevicesMeaningSealed ScanState
falsenullnever scannedIdle
true[…]scanning, these found so farScanning(found)
false[…]finished with theseFinished(found)
truenullnothing, but the types allow itcan't be written

A sealed interface (Lesson 01, section 2) lists exactly the three real states, each carrying only the data that state has. Every when over it must handle all three, so adding a fourth state later makes the compiler point at every Kotlin screen that needs updating. Swift doesn't get that check yet (section 5); Lesson 09 brings it.

Errors are state, too. A scan failure needs a dialog shown once. It's tempting to send it as a one-off "event" through a Channel or SharedFlow. Android's guidance is direct: "ViewModel events should always result in a UI state update", because with Channels or other streams, "when the producer (the ViewModel) outlives the consumer (Compose UI), these solutions don't guarantee the delivery and processing of those events". So the message goes into the state, and when the UI has shown it, it calls back so the ViewModel clears it: "Either the user message is displayed, or it isn't" (UI events). Here that's errorMessage plus errorShown(). A bonus: the dialog survives rotation, because it's just state.

What stays in the UI. The filter text is input: the user owns it while typing, and the ViewModel only needs it when Scan is tapped. So it stays where m02 had it (rememberSaveable, @State, or the text field itself) and goes to the ViewModel as an argument: startScan(filter). Every keystroke then stays synchronous on every track, with no round trip through a flow.

From TypeScriptScanState is a discriminated union: type ScanState = { kind: "idle" } | { kind: "scanning"; found: Device[] } | { kind: "finished"; found: Device[] }. Kotlin's when is a switch with the never exhaustiveness check built in. it.copy(scan = …) is { ...state, scan: … }. A StateFlow is an RxJS BehaviorSubject (or an Angular signal): it always has a current value, and a new subscriber gets that value first. viewModelScope is takeUntil(destroy$) applied to everything the ViewModel starts.

3. The shared code

Four files in shared/: the build file gains the ViewModel library, and three new Kotlin files hold the scanner, the state, and the ViewModel. The m02 files (Device.kt, SampleDevices.kt) stay as they are, and so does the root build file: Kotlin stays at 2.4.21 in this lesson.

  1. androidx.lifecycle:lifecycle-viewmodel is Google's multiplatform ViewModel, the same artifact Android apps use (KMP ViewModel). Version 2.11.0 matches the lifecycle libraries already in the app.
  2. api, not implementation: ViewModel and StateFlow appear in the shared module's public API (the ViewModel extends one and exposes the other), so modules that use :shared need them too. With api the Android app gets coroutines through :shared, so it no longer depends on them only by accident through another library (Lesson 06, section 5, noted that Compose got them through the Compose runtime).
  3. export(…) puts the library's classes into the iOS framework's public header under their own names, so Swift can use ViewModel and ViewModelStore (section 5). Android's guide calls for it: "You need the api dependency declaration here if you want better access to the classes from Swift code."
  4. binaryOption("bundleId", …): as soon as we exported a library, the Kotlin/Native linker warned Cannot infer a bundle ID from packages of source files and exported dependencies, use the bundle name instead: Shared. Naming the bundle ID explicitly silences it. The course treats warnings as errors.
  1. flow { … } builds a cold Flow (Asynchronous Flow, Lesson 01, section 5): nothing runs until someone collects it, and each collector gets its own run. emit(device) hands one value to the collector, and delay(300) suspends without blocking a thread (Lesson 07, section 3).
  2. awaitCancellation() suspends forever. A real BLE scan has no end, and it reports devices until you stop it. Making the fake behave the same way forces the ViewModel to stop it properly, so the ViewModel's stopping code already works when a real scanner arrives.
  3. ScanException is our own type, so the ViewModel can catch exactly this failure and nothing else (the ViewModel's point 6 below). The "fail" filter is a test hook, so you can reach the error path by hand. From Lesson 11, tests drive a fake scanner they control instead.
  1. One immutable data class for the screen. Default values make DeviceListUiState() the initial state. Changes always produce a new object with copy.
  2. data object Idle is a singleton with a readable toString. Scanning and Finished carry the devices found, because only those states have any.

The ViewModel comes in two excerpts. First its shape: what it holds, what it exposes, and how it gets built.

Then the two events. startScan holds most of the lesson's Kotlin:

  1. The backing property. _uiState is a private MutableStateFlow; the public uiState is read-only (asStateFlow()). Only the ViewModel can change state, and everyone else can only observe it. "StateFlow is a state-holder observable flow that emits the current and new state updates to its collectors" (StateFlow and SharedFlow).
  2. _uiState.update { it.copy(…) } computes the new state from the current one and swaps it in atomically. It's never _uiState.value.scan = …, because the state is immutable.
  3. if (scanJob?.isActive == true) return: a second startScan during a scan is ignored. The disabled button already prevents it, but the ViewModel shouldn't rely on its UI for correctness.
  4. State first, then launch. Scanning(emptyList()) is set synchronously, so the very next frame shows the spinner: the rule from Lessons 06 and 07. Then viewModelScope.launch starts the slow part in the ViewModel's own scope. On both platforms it runs on the main thread (Dispatchers.Main.immediate), and delay keeps it from blocking. That's how the ViewModel publishes UI state on the main thread, as Lesson 07 promised.
  5. withTimeoutOrNull(SCAN_TIMEOUT) cancels the block after 3 s and returns null instead of throwing, so execution continues to the Finished line. This is how a never-ending scan stops "on timeout" (requirement A.3).
  6. catch (e: ScanException), not catch (e: Exception). When the scope is cancelled (ViewModel cleared), a CancellationException flies through this code. Catching every Exception would swallow it and keep a dead ViewModel's coroutine running. Catch only what you can handle.
  7. found.toList() on every update hands the state a copy. A StateFlow only emits a value that isn't equals to the current one. If the state shared the mutable list, the "new" state would already equal the old one. You'll test this in the unaided exercise.
  8. Factory tells the platform how to build this ViewModel, because the platform creates it, not you. viewModelFactory { initializer { … } } is the multiplatform way to write one. Both Android tracks and both iOS tracks use this same factory.
Keep an eye on this line initializer { DeviceListViewModel(FakeDeviceScanner()) }: the ViewModel's own factory picks a concrete scanner, and the constructor asks for FakeDeviceScanner by name. Today that's fine, because there is only one scanner. But Lesson 13 needs a different scanner on each platform (an Android radio and a Swift CoreBluetooth class), and Lesson 11's tests need one they control. Neither can be passed in while the ViewModel names its scanner's class. That's the problem Lesson 10 starts from.

4. Android: collect while visible

Collecting from the ViewModel is a different job from owning it. The UI collects only while it's on screen: "collection begins when the lifecycle is STARTED and stops when the lifecycle is STOPPED" (coroutines with lifecycle-aware components). The ViewModel keeps working the whole time, so when the UI starts collecting again, the StateFlow hands it the latest state first.

  1. viewModel(factory = DeviceListViewModel.Factory) (from lifecycle-viewmodel-compose, the one new dependency) returns the ViewModel of the nearest ViewModelStoreOwner. Inside a NavHost that owner is the navigation entry, so the ViewModel lives while the list is on the back stack. It survives the trip to the detail screen and rotation, and it's cleared when the entry is popped. As a default parameter, it can be replaced by a fake in a preview or test.
  2. collectAsStateWithLifecycle() turns the StateFlow into Compose State and collects only while the screen is at least STARTED. Android calls it "the recommended way to collect flows on Android apps". Plain collectAsState is the platform-agnostic version, which keeps collecting in the background (State and Jetpack Compose).
  3. DeviceListContent didn't change. Lessons 06 and 07 split the screen into a stateful wrapper and stateless content, and promised that a ViewModel would replace only the wrapper. That's what happened. remember, rememberCoroutineScope, delay and SampleDevices all left this file.
  4. when (val scan = state.scan) maps the sealed state onto the content's two parameters. There's no else branch: the compiler checks that all three cases are handled.
  5. The dialog is state. It exists while errorMessage is non-null. Both "OK" and dismissing (tap outside, Back) call errorShown(), which clears the message, and the next recomposition removes the dialog. Rotation can't lose it.
  6. viewModel::errorShown is a function reference, a lambda that calls errorShown() on that instance.

androidApp/build.gradle.kts is unchanged. viewModels comes from fragment-ktx, repeatOnLifecycle from lifecycle-runtime-ktx, and the factory helpers and coroutines from :shared (api).

  1. by viewModels { DeviceListViewModel.Factory } (from fragment-ktx) scopes the ViewModel to this Fragment. It's created on first access, survives rotation (the Fragment is recreated, but its ViewModelStore isn't), and is cleared when the Fragment leaves the back stack for good.
  2. The state fields are gone, and so are onSaveInstanceState and onCreate. The Fragment holds no screen state any more, only views and the ViewModel reference.
  3. viewLifecycleOwner.repeatOnLifecycle(STARTED) runs the collect block "every time the lifecycle is in the STARTED state (or above)" and "cancels it when it's STOPPED" (coroutines with Views). Use the view lifecycle, not the Fragment's: the views die while the Fragment sits on the back stack, and render must never touch dead views.
  4. render(state) is m02's render(), now with the state as a parameter instead of fields. Every emission ends here, and nothing else touches a widget.
  5. The EditText keeps the filter. It owns its text while the user types, restores it after rotation (it has an id), and is read once, when Scan is tapped.
  6. The red colour gained && !isScanning. A scan now starts as Scanning(found = []). m02's rule (devices?.isEmpty() == true) would paint "Scanning…" red, the same kind of bug as the imperative phone in Lesson 06's toy. Compose and SwiftUI never hit this, because their when/if checks isScanning first. Hand-written render() code computes each widget separately, so each derivation has to be checked again.
  7. The dialog is shown when the state has a message and no dialog is up. "OK" and cancel (Back, tap outside) call errorShown(). In onDestroyView, dismiss() removes the window without calling the cancel listener, so after rotation the message is still in state and the new view shows the dialog again.

XML vs Compose · what changed and whyBoth tracks now look the same from the ViewModel's side: get it from the nearest owner (Navigation entry or Fragment), collect while STARTED, render. The Compose version deleted its stateful code and kept its content. The XML version deleted its fields and saved state, but kept its render(). The only XML-only bug came from render() computing each widget separately.

Two jobs, then. Own the ViewModel, so it's cleared when the screen goes. Observe its StateFlow, which Swift can't do directly. The diagram shows the pieces this section writes for each job.

  • Shared ViewModel

Owning: there is no ViewModelStoreOwner on iOS

"SwiftUI on iOS, however, has no built-in equivalent for the AndroidX ViewModel" (KMP ViewModel). So we write the owner: a Swift class holding a ViewModelStore, which clears it in deinit. These two files follow Android's guide, and both iOS tracks use them. They stay after Lesson 09.

  1. ViewModelProvider.create(store, factory)[vmClass] is what Android does behind viewModels. It returns the store's instance if there is one, and otherwise builds one with the factory and stores it. So calling owner.viewModel(…) repeatedly always returns the same ViewModel.
  2. Why a Kotlin helper? The provider wants a KClass, and Swift can only pass an Objective-C class (VM.self). getOriginalKotlinClass converts it back. It's marked @BetaInteropApi, hence the opt-in. @Throws turns the require failure into a Swift throws.
  3. deinit { store.clear() } is the point of the class. Clearing the store calls each ViewModel's onCleared() and cancels its viewModelScope. Without it, a ViewModel's work outlives its screen (section 6's first gotcha).
  4. Creating the owner is cheap on purpose. You'll keep it in @State, and Apple warns: "A State property always instantiates its default value when SwiftUI instantiates the view. For this reason, avoid side effects and performance-intensive work when initializing the default value" (State). An empty store costs nothing. The ViewModel itself is created on first use.

Observing: a hand-written bridge

The bridge needs a Kotlin class that collects the flow and calls Swift back. It must be a class, because only classes keep their generic type in Swift. This file is temporary: Lesson 09 deletes it.

  1. class StateFlowWatcher<T : Any>: Swift writes StateFlowWatcher<DeviceListUiState>(flow: viewModel.uiState), and value and the callback come back typed. T : Any makes them non-optional in Swift.
  2. MainScope() runs the collection on the main thread (Dispatchers.Main), so Swift's callback can touch UI. A StateFlow delivers its current value first, then every new one.
  3. Watch is the handle Swift keeps. cancel() cancels the scope, which stops the collection. Forgetting to cancel it would keep collecting forever.

SwiftUI needs one more piece. A SwiftUI view re-renders when observable state that its body read changes, and a Kotlin callback isn't observable. So a small Swift class owns the ViewModel and copies each new state into a property marked for observation. @Observable (the Observation framework, iOS 17) makes a class's stored properties tracked: a view that reads state in its body is updated when state changes.

  1. DeviceListObserver is an @Observable class with one tracked property, state. The watcher's callback assigns to it, and SwiftUI re-renders whatever read it. @ObservationIgnored keeps the plumbing out of observation.
  2. [weak self]: the Kotlin scope holds the callback, and the callback must not keep the observer alive. When SwiftUI drops the observer, its deinit cancels the watch, and then the owner's deinit clears the ViewModel.
  3. The init does real work (it creates the ViewModel and starts watching), against Apple's @State advice above. For a root screen that SwiftUI creates once, this is harmless. Lesson 09 moves the work out of the initializer.
  4. The screen is now split like Compose's: DeviceListView owns the filter and talks to the ViewModel, and DeviceListContent only renders. Its body is m02's DeviceListView body, with onScan in place of scan(). ScanStatus and DeviceRow are unchanged. filter is plain @State, passed down as a binding and read when Scan is tapped.
  5. devices(in:) casts with as?, because ScanState reaches Swift as a protocol. If a fourth case is added, this function returns nil for it, and nothing warns you.
  6. The alert binding reads errorMessage != nil. When the user taps OK, SwiftUI sets it to false, and that calls errorShown().
  1. private let owner = ViewModelOwner(): the view controller is the owner's owner. When the view controller is deallocated (popped, or its window closed), the ViewModel is cleared. lazy var viewModel creates it on first use, after owner exists.
  2. Watch in viewWillAppear, cancel in viewDidDisappear: UIKit's version of repeatOnLifecycle(STARTED), using the view lifecycle from Lesson 04. watch?.cancel() before starting a new watch costs nothing and guarantees there is never more than one. While the detail screen is pushed, nothing renders into hidden views. The ViewModel keeps scanning, and when the list reappears, the first value it receives is the latest state.
  3. [weak self] in the callback: the Kotlin scope holds the closure, and the closure must not keep the view controller alive.
  4. viewDidLoad renders value once, so the first frame isn't blank before the watch starts.
  5. render(_:) is m02's render() with the state as a parameter. The as? chain replaces a switch, because ScanState reaches Swift as a protocol. The red colour gained && !isScanning: a scan now starts as Scanning(found = []), so m02's rule (devices?.isEmpty == true) alone would paint "Scanning…" red. SwiftUI never hits it, because its if checks isScanning first. A hand-written render() computes each widget separately, so each derivation has to be checked again.
  6. renderError presents an alert when there's a message and nothing is presented already. OK calls errorShown(). The text field owns the filter, and the Scan action reads it.

UIKit vs SwiftUI · what changed and whySame owner, same watcher. SwiftUI needs an @Observable object in between, because a view can only re-render from observable state, while UIKit's callback calls render directly. UIKit decides when to observe (viewWillAppear/viewDidDisappear). The SwiftUI observer watches for its whole life, which for the root screen is the app's life.

Gotcha · Swift 6 rejects the obvious bridge The first attempt wrapped the watcher in an AsyncStream, so SwiftUI could for await it in .task. Swift 6 stopped it twice: capture of 'watch' with non-Sendable type 'Watch' in a '@Sendable' closure, and after that was worked around, sending '$0' risks causing data races. Kotlin classes reach Swift without any Sendable information, so every hop across a concurrency boundary is suspect. The callback-into-@Observable shape above crosses no such boundary, so it compiles clean. In Lesson 09, SKIE generates bridges that satisfy the checker for you.

6. What actually happens

We built m03 (Kotlin 2.4.21, Lifecycle 2.11.0, coroutines 1.11.0, AGP 9.4.1, Xcode 26.2) on all four tracks, and ran it on the Android 16 emulator and the iOS 26.2 simulator. Tap Scan: rows appear one by one under "Scanning…", every 0.3 s. At 3 s the scan stops and the status reads "Devices found: 5". Rotate during a scan: it carries on, and the new screen finishes with all five devices (in m02, it fell back to "Tap Scan"). The filter fail shows a "Scan failed" dialog that survives rotation and goes away on OK.

m03 is a natural stop. It's done when both apps build and behave as above. Commit it before the next lesson, which starts from this state.

Gotcha · iOS: a ViewModel without an owner keeps working after its screen is gone We held the ViewModel directly in @State (no ViewModelOwner), started a scan, and replaced the list view mid-scan. The log showed two scans interleaving: the new screen's, and the old ViewModel's, still finding devices for a screen that no longer existed. onCleared() never ran. With the owner, the old ViewModel was cleared at once and its scan stopped. With a real radio, that orphaned scan is a battery drain nobody can see. Every shared ViewModel on iOS needs an owner that clears it.
Gotcha · ViewModelStore.put compiles from Swift, but isn't yours to call Our first owner called store.put(key:viewModel:) directly, and it worked. But put is @RestrictTo(LIBRARY_GROUP) in the Lifecycle sources: internal to AndroidX, free to change. Android lint would flag it in Kotlin, but nothing checks Swift. Hence the public ViewModelProvider route in ViewModelResolver.kt.

Retrieval checks

Answer from memory, without scrolling up.

Where does the scan coroutine run in m03?

It's launched in viewModelScope, so it lives as long as the ViewModel and is cancelled when the ViewModel is cleared.

The error dialog is open and the user rotates the phone. What happens?

errorMessage stays non-null until errorShown(), so the new screen renders the dialog again. That's why Android recommends state over event streams.

Why must Swift's ViewModel owner clear the store in deinit?

Memory would be reclaimed anyway. Without clear(), onCleared never runs and coroutines in viewModelScope keep going: the orphaned scan in section 6.

In m03, what type does Swift give viewModel.uiState.value?

StateFlow is an interface, which becomes an Objective-C protocol, and protocols keep no generics. That's why StateFlowWatcher is a class.

Where does the "Scan failed" message live while the dialog is showing?

The message is part of DeviceListUiState. The UI shows a dialog while it's non-null and reports back with errorShown(). A Channel can lose it: if the screen stops collecting (a rotation, say) just as the message is handed over, the message is gone.

Mixed review (interleaved)

After rotating, the m03 list collects uiState again. What does a new collector receive first? (Lesson 01)

A StateFlow always has a value and replays exactly that one to each new collector. That's why rotation shows the scan in progress immediately.

On iOS, does rotating the phone recreate the list screen? (Lesson 07)

iOS doesn't recreate view controllers or views on rotation. The ViewModel still matters on iOS: it keeps work out of views and shares the logic with Android.

Swift writes ScanStateIdle.shared for Kotlin's ScanState.Idle. Why .shared? (Lesson 05)

data object Idle is an object, and the Objective-C header exposes every Kotlin object as .shared, like SampleDevices.shared. When Swift can't find a Kotlin name, the answer is in Shared.h.

import kotlinx.coroutines.delay

class ScanException(message: String) : Exception(message)

// Stand-in for the BLE scanner of Lesson 13. Like a real scan, devices arrive one at a
// time and the flow never completes on its own: the collector stops it by cancelling.
class FakeDeviceScanner {
    fun scan(filter: String): Flow<Device> = flow {
        // Test hook for now: the filter "fail" simulates a radio error.
        if (filter.trim().equals("fail", ignoreCase = true)) {
            delay(500)
            throw ScanException("Bluetooth adapter not responding (simulated).")
        }
        for (device in SampleDevices.matching(filter)) {
            delay(300)
            emit(device)
        }
        awaitCancellation()
    }
}

package com.example.devicemonitor

import androidx.lifecycle.ViewModel
import androidx.lifecycle.ViewModelProvider
import androidx.lifecycle.viewModelScope
import androidx.lifecycle.viewmodel.initializer
import androidx.lifecycle.viewmodel.viewModelFactory
import kotlinx.coroutines.Job
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch
import kotlinx.coroutines.withTimeoutOrNull
import kotlin.time.Duration.Companion.seconds

class DeviceListViewModel(
    private val scanner: FakeDeviceScanner,
) : ViewModel() {
    private val _uiState = MutableStateFlow(DeviceListUiState())
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                withTimeoutOrNull(SCAN_TIMEOUT) {
                    scanner.scan(filter).collect { device ->
                        found += device
                        _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                    }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    companion object {
        val SCAN_TIMEOUT = 3.seconds

        val Factory: ViewModelProvider.Factory = viewModelFactory {
            initializer { DeviceListViewModel(FakeDeviceScanner()) }
        }
    }
}

package com.example.devicemonitor

import androidx.lifecycle.ViewModel
import androidx.lifecycle.ViewModelProvider
import androidx.lifecycle.ViewModelStore
import kotlinx.cinterop.BetaInteropApi
import kotlinx.cinterop.ObjCClass
import kotlinx.cinterop.getOriginalKotlinClass
import kotlin.reflect.KClass

// Swift can't pass a KClass, only its Objective-C class. This turns it back into the
// KClass that ViewModelProvider needs. Adapted from Android's KMP ViewModel guide.
@OptIn(BetaInteropApi::class)
@Throws(IllegalArgumentException::class)
fun ViewModelStore.resolveViewModel(
    modelClass: ObjCClass,
    factory: ViewModelProvider.Factory,
): ViewModel {
    @Suppress("UNCHECKED_CAST")
    val vmClass = getOriginalKotlinClass(modelClass) as? KClass<ViewModel>
    require(vmClass != null) { "The modelClass parameter must be a ViewModel type." }
    return ViewModelProvider.create(this, factory)[vmClass]
}

package com.example.devicemonitor

import kotlinx.coroutines.MainScope
import kotlinx.coroutines.cancel
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.launch

// Until Lesson 09: lets Swift observe a StateFlow without SKIE. Lesson 09 deletes this file.
class StateFlowWatcher<T : Any>(private val flow: StateFlow<T>) {
    val value: T get() = flow.value

    // Calls onEach on the main thread with the current value, then with every new one,
    // until the returned Watch is cancelled.
    fun watch(onEach: (T) -> Unit): Watch {
        val scope = MainScope()
        scope.launch { flow.collect { onEach(it) } }
        return Watch { scope.cancel() }
    }
}

class Watch(private val onCancel: () -> Unit) {
    fun cancel() = onCancel()
}
iosApp/iosApp/ViewModelOwner.swift 
import Shared

// iOS has no ViewModelStoreOwner, so this class plays that role. Keep it in a view's
// @State (or a view controller's property). When it is deinitialised, clearing the store
// cancels every viewModelScope in it and calls onCleared().
final class ViewModelOwner {
    private let store = ViewModelStore()

    // Returns the store's instance of VM, creating it with the factory on first use.
    func viewModel<VM: ViewModel>(factory: any ViewModelProviderFactory) -> VM {
        do {
            return try store.resolveViewModel(modelClass: VM.self, factory: factory) as! VM
        } catch {
            fatalError("Couldn't create \(VM.self): \(error)")
        }
    }

    deinit {
        store.clear()
    }
}

class DeviceListFragment : Fragment() {

    private var binding: FragmentDeviceListBinding? = null
    private var errorDialog: AlertDialog? = null
    private val adapter = DeviceAdapter { device ->
        val nav = findNavController()
        // A fast double tap delivers two clicks; only navigate from the list itself.
        if (nav.currentDestination?.id == R.id.deviceList) {
            nav.navigate(R.id.toDetail, Bundle().apply { putString("deviceId", device.id) })

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {

        binding = b

        b.deviceList.addItemDecoration(DividerItemDecoration(requireContext(), DividerItemDecoration.VERTICAL))
        b.scanButton.setOnClickListener { viewModel.startScan(b.filterInput.text.toString()) }

        super.onViewCreated(view, savedInstanceState)
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { render(it) }
            }
        }

    override fun onDestroyView() {
        super.onDestroyView()
        errorDialog?.dismiss() // a dismiss() doesn't call the cancel listener, so the error stays in state
        errorDialog = null
        binding?.deviceList?.adapter = null // the adapter outlives the view; don't let it keep the old list
        binding = null
    }

    // The one place that touches views: every new state ends here. The EditText keeps its
    // own text (and restores it after rotation), so render() never sets it.
    private fun render(state: DeviceListUiState) {
        val b = binding ?: return
        val isScanning = state.scan is ScanState.Scanning
        val devices = when (val scan = state.scan) {
            ScanState.Idle -> null
            is ScanState.Scanning -> scan.found
            is ScanState.Finished -> scan.found

        b.scanButton.isEnabled = !isScanning
        b.progress.visibility = if (isScanning) View.VISIBLE else View.GONE
        b.statusText.text = when {
            isScanning -> "Scanning…"
            devices == null -> "Tap Scan to look for devices."
            devices.isEmpty() -> "No devices found. Try another filter."
            else -> "Devices found: ${devices.size}"
        }
        b.statusText.setTextColor(if (devices?.isEmpty() == true && !isScanning) Color.RED else Color.DKGRAY)
        adapter.submitList(devices.orEmpty())
        renderError(state.errorMessage)
    }

    private fun renderError(message: String?) {
        if (message == null) {
            errorDialog?.dismiss()
            errorDialog = null
        } else if (errorDialog == null) {
            errorDialog = AlertDialog.Builder(requireContext())
                .setTitle("Scan failed")
                .setMessage(message)
                .setPositiveButton("OK") { _, _ -> viewModel.errorShown() }
                .setOnCancelListener { viewModel.errorShown() }
                .show()
        }
    }
}

@Observable
final class DeviceListObserver {
    @ObservationIgnored let viewModel: DeviceListViewModel
    private(set) var state: DeviceListUiState

    @ObservationIgnored private let owner: ViewModelOwner
    @ObservationIgnored private var watch: Watch?

    init() {
        let owner = ViewModelOwner()
        let viewModel: DeviceListViewModel = owner.viewModel(factory: DeviceListViewModel.companion.Factory)
        let watcher = StateFlowWatcher<DeviceListUiState>(flow: viewModel.uiState)
        self.owner = owner
        self.viewModel = viewModel
        self.state = watcher.value
        watch = watcher.watch { [weak self] newState in
            self?.state = newState
        }
    }

    deinit {
        watch?.cancel()
    }
}

import UIKit
import Shared

final class DeviceListViewController: UIViewController, UITableViewDelegate {
    private let owner = ViewModelOwner()
    private lazy var viewModel: DeviceListViewModel = owner.viewModel(factory: DeviceListViewModel.companion.Factory)
    private var watch: Watch?

    private let filterField = UITextField()
    private let scanButton = UIButton(configuration: .filled())
    private let spinner = UIActivityIndicatorView(style: .medium)
    private let statusLabel = UILabel()
    private let tableView = UITableView()
    private lazy var dataSource = UITableViewDiffableDataSource<Int, String>(tableView: tableView) {
        tableView, indexPath, deviceId in
        let cell = tableView.dequeueReusableCell(withIdentifier: "device", for: indexPath)
        var content = UIListContentConfiguration.subtitleCell()
        if let device = SampleDevices.shared.find(id: deviceId) {
            content.text = device.name
            content.secondaryText = "\(device.id)   \(device.rssi) dBm"
        }
        cell.contentConfiguration = content
        cell.accessoryType = .disclosureIndicator
        return cell
    }

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "Device Monitor"
        navigationController?.navigationBar.prefersLargeTitles = true
        view.backgroundColor = .systemBackground

        filterField.placeholder = "Device name filter"
        filterField.borderStyle = .roundedRect
        filterField.autocorrectionType = .no
        scanButton.configuration?.title = "Scan"
        scanButton.addAction(UIAction { [weak self] _ in
            guard let self else { return }
            viewModel.startScan(filter: filterField.text ?? "")
        }, for: .touchUpInside)
        statusLabel.numberOfLines = 0
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "device")
        tableView.delegate = self

        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let stack = UIStackView(arrangedSubviews: [filterField, scanButton, statusRow, tableView])
        stack.axis = .vertical
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
            stack.bottomAnchor.constraint(equalTo: view.bottomAnchor),
        ])
        render(StateFlowWatcher<DeviceListUiState>(flow: viewModel.uiState).value)
    }

    // Collect only while on screen, like repeatOnLifecycle(STARTED) on Android.
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        watch?.cancel()
        watch = StateFlowWatcher<DeviceListUiState>(flow: viewModel.uiState).watch { [weak self] state in
            self?.render(state)
        }
    }

    override func viewDidDisappear(_ animated: Bool) {
        super.viewDidDisappear(animated)
        watch?.cancel()
        watch = nil
    }

    // The one place that touches views: every new state ends here. The text field owns
    // its own text, so render() never sets it.
    private func render(_ state: DeviceListUiState) {
        let isScanning = state.scan is ScanStateScanning
        // Without SKIE, Swift sees ScanState as a protocol: no exhaustive switch, so cast.
        let devices: [Device]? = if let scanning = state.scan as? ScanStateScanning {
            scanning.found
        } else if let finished = state.scan as? ScanStateFinished {
            finished.found
        } else {
            nil
        }
        scanButton.isEnabled = !isScanning
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let devices {
            statusLabel.text = devices.isEmpty
                ? "No devices found. Try another filter."
                : "Devices found: \(devices.count)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = devices?.isEmpty == true && !isScanning ? .systemRed : .label

        var snapshot = NSDiffableDataSourceSnapshot<Int, String>()
        snapshot.appendSections([0])
        snapshot.appendItems((devices ?? []).map(\.id))
        dataSource.apply(snapshot, animatingDifferences: true)
        renderError(state.errorMessage)
    }

    private func renderError(_ message: String?) {
        guard let message, presentedViewController == nil else { return }
        let alert = UIAlertController(title: "Scan failed", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default) { [weak self] _ in
            self?.viewModel.errorShown()
        })
        present(alert, animated: true)
    }

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        guard let deviceId = dataSource.itemIdentifier(for: indexPath) else { return }
        navigationController?.pushViewController(DeviceDetailViewController(deviceId: deviceId), animated: true)
    }
}
