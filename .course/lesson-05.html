Anatomy of a KMP Project

~2.5 h · +0.25 h per extra UI track Milestone: m00 skeleton Prereq: 04
Why this matters: every later lesson adds code to one project with three parts: a shared Kotlin module, an Android app, and an iOS app. Today you build that project's skeleton, milestone m00. Both apps show a greeting that comes from shared Kotlin, and part of the greeting is computed differently on each platform. Once you can trace that greeting from a .kt file to an iPhone screen, you can find your way around any KMP codebase, including the team's.

Primary source JetBrains' The basics of Kotlin Multiplatform project structure. It's short, and it defines targets and source sets exactly as this lesson uses them. Read it after section 1.

Tracks The shared module is identical on every track. Only the few lines that put the greeting on screen differ. Each excerpt below shows only the lines its notes explain, and the complete files are in Full files at the end.

1. Two words: target and source set

A target is a platform the Kotlin compiler builds your code for: here android, iosArm64 (real iPhones) and iosSimulatorArm64 (the simulator on an Apple-silicon Mac). There's no single "iOS" target. A device and a simulator need separate binaries (JetBrains: project structure).

A source set is a folder of Kotlin files plus the list of targets it compiles to. That list decides which APIs the code may call:

  • Android
  • iOS

To compile one target, Kotlin takes every source set labelled with it and compiles them together. The Android binary is commonMain + androidMain; the simulator binary is commonMain + iosMain. iosMain is an intermediate source set: it serves two targets, so you write iOS code once instead of once per architecture. Kotlin creates it (and appleMain, nativeMain) automatically through its default hierarchy (JetBrains: hierarchical project structure).

From TypeScriptThink of a monorepo with one core package that both a web and a mobile app import. The difference: core here compiles to different machine code per platform (JVM bytecode for Android, a native binary for iOS), and the compiler refuses platform APIs in the shared folder instead of crashing at runtime.

2. The project on disk

The project has three parts. Gradle builds shared and androidApp. Xcode builds iosApp, and asks Gradle for the shared code before it compiles any Swift (section 7).

  • Android
  • iOS

JetBrains' project wizard generates the same layout; newer wizard versions name the module sharedLogic instead of shared (JetBrains: share more logic).

3. The shared module's build file

  1. Two plugins. kotlin.multiplatform provides the kotlin { } block, targets and source sets. com.android.kotlin.multiplatform.library is Google's plugin for the Android target of a KMP library. The older com.android.library route is deprecated from AGP 9 (Android: KMP library plugin).
  2. android { } sits inside kotlin { }. Since AGP 8.12 the Android target is configured there. Tutorials showing androidLibrary { } are older, and that name is deprecated. compileSdk and minSdk mean what they meant in Lesson 03. targetSdk is set only in the app module (section 5).
  3. Declaring a target is one call: iosArm64() and iosSimulatorArm64() each add a target and return it. We loop over both to give each one the same output.
  4. binaries.framework makes each iOS target produce an Apple framework, a bundle containing the compiled binary plus a header that Swift can import. baseName = "Shared" is the name Swift uses: import Shared. isStatic = true links the Kotlin code straight into the app binary.
  5. No sourceSets { } block: the folders in section 2 follow the default naming, so Gradle finds them on its own. You add that block in Lesson 08, when commonMain gets its first library.

4. expect / actual: one name, a body per platform

Shared code sometimes needs one small fact only the platform knows, such as the OS version. commonMain can't call android.os.Build, so it declares what it needs with expect, and each platform source set supplies it with actual (JetBrains: expected and actual declarations):

  • Android
  • iOS
  1. The expect has no body. It's a promise, and the compiler checks that every target keeps it. Same package, same name, same signature.
  2. actual marks the platform's implementation. The file names (Platform.android.kt, Platform.ios.kt) are only a convention. The package and the folder decide what matches.
  3. import platform.UIKit.UIDevice is Kotlin calling Apple's UIKit directly. Kotlin/Native ships bindings for Apple frameworks under platform.*, so iosMain can call them without any Swift. Lesson 17's log store uses this style. Note systemName() is called as a method while systemVersion is a property. That's how the bindings expose these two; let the IDE's autocomplete tell you which form each API takes.
  4. Greeting is ordinary common code. It calls platformName() without knowing which body runs. That decision is made at compile time, per target.
When not to use expect/actual JetBrains' own advice is to prefer ordinary language features: a common interface with one implementation per platform, injected where it's needed (same page). An interface can have a fake implementation in tests, and the iOS implementation can be written in Swift. That's exactly what the course's outbound ports are from Lesson 10 on (BleScanner, PermissionChecker, …). Keep expect/actual for small facts like this one. Expected classes are still Beta and print a compiler warning.

5. Android: shared is just another module

To the Android app, :shared is an ordinary library module. One dependency line makes Greeting importable, and Gradle compiles commonMain + androidMain into the APK:

  1. implementation(project(":shared")) is the whole integration. Gradle builds the shared module's Android variant first. There's no framework and no copying.
  2. The app's namespace (…devicemonitor.android) differs from the shared module's (…devicemonitor.shared). Every Android module needs its own namespace, because each one generates its own R class.
  3. import com.example.devicemonitor.Greeting is the package from commonMain. The Android app can't tell shared code from its own.
  4. .MainActivity in the manifest is resolved against the app's namespace, so it means com.example.devicemonitor.android.MainActivity. exported="true" is required for any activity with an intent filter (targetSdk 31+).
  5. Edge-to-edge, two halves. With targetSdk 35 and higher, apps draw behind the system bars by default (Android: edge-to-edge). enableEdgeToEdge() makes the bars transparent and picks status-bar icon colours that match the theme; without it, our first build showed white icons on the light background. safeDrawingPadding() then keeps the text out from under the bars.fitsSystemWindows="true" on the root then pads the layout clear of the bars. The text's own spacing is a margin, because fitsSystemWindows replaces the root's padding.

XML vs Compose · what changed and whyOnly the last line of onCreate differs: a TextView found by id and assigned, versus a Text composable given the string. The dependency on :shared and the call Greeting().greet() are identical. That's the point of the architecture: shared code never knows which UI track renders it.

6. iOS: Swift sees Kotlin through a header

Xcode can't read .kt files. Kotlin/Native compiles commonMain + iosMain into the Shared framework, and generates an Objective-C header that describes its API. Swift imports that header like any Apple framework (JetBrains: interop with Swift/Objective-C). Most names come through unchanged, with a few patterns to know:

KotlinSwift sees
class Greeting with fun greet(): StringGreeting().greet() → String
a top-level function in Platform.ios.ktPlatform_iosKt.platformName(): a class named after the file
object FooFoo.shared
interface · List · Unitprotocol · Array · Void
suspend fun, Flow, sealed typesusable but awkward: Lesson 09 fixes this with SKIE

We confirmed the first two rows by reading the generated header: shared/build/bin/iosSimulatorArm64/debugFramework/Shared.framework/Headers/Shared.h. Read it yourself after your first build. When Swift can't find a Kotlin name, the answer is in that file.

  1. import Shared is the framework's baseName from section 3. Nothing else is needed to see Greeting.
  2. Greeting() creates a Kotlin object from Swift. Kotlin/Native manages its memory, and you don't free it.
  3. greet() returns a Swift String; the conversion happens at the boundary.
  4. The string is computed once, when the view struct is created, and stored in a let. Lesson 06 introduces state that changes over time.The label spans the layout margins with numberOfLines = 0, so a long greeting wraps instead of being cut off.
  5. iOSApp.swift is the same @main App you wrote in Lesson 04, minus the logging. It shows ContentView() in a WindowGroup and never touches shared code.AppDelegate.swift and SceneDelegate.swift are Lesson 04's with the logging removed, except that the scene delegate's root is ViewController() itself, not a navigation controller wrapping it. Neither touches shared code. project.yml keeps Lesson 04's UIApplicationSceneManifest, or the scene delegate never runs.

UIKit vs SwiftUI · what changed and whyUIKit needs three files to show one label (app delegate, scene delegate, view controller) because you build the window and the view tree yourself. SwiftUI needs two. In both, the line that touches shared code is the same: import Shared and Greeting().greet().

7. How Xcode gets the framework

We use JetBrains' direct integration: a script build phase in the Xcode target runs Gradle on every build (JetBrains: direct integration):

  • iOS

Because the framework is static, the finished iosApp.app has no Frameworks/ folder: Kotlin and Swift are linked into the same binary. (In Debug builds Xcode puts that code in iosApp.debug.dylib next to a small launcher stub; Release builds produce a single executable.)

In XcodeGen, the build phase is a preBuildScripts entry. ENABLE_USER_SCRIPT_SANDBOXING: NO is needed because the script must read and write outside Xcode's sandbox (the shared/ folder and ~/.gradle). basedOnDependencyAnalysis: false turns off Xcode's "Based on dependency analysis" checkbox, so the script runs on every build and Gradle decides what is up to date. The other ways to ship Kotlin to iOS are a Swift package or CocoaPods. They matter when a separate team consumes the framework, not for one repo like ours.

Gotcha · a green Android build doesn't prove commonMain is common We put android.os.Build.MODEL into Greeting.kt (commonMain) on purpose. ./gradlew :androidApp:assembleDebug still succeeded: the Android compilation of commonMain sees the Android SDK. Only an iOS build, or ./gradlew :shared:compileCommonMainKotlinMetadata, failed with Unresolved reference 'android'. The IDE highlights it too, but if you only build Android, you find out on the iOS side, later. Run the metadata compile (seconds) after touching commonMain.
Gotcha · the build-setup failures
  • Gradle daemon dies with "out of JVM Metaspace": an Android + Kotlin/Native build needs more memory than Gradle's default. Set org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g in gradle.properties. We hit exactly this on the first build.
  • The Xcode script fails with ⛔ User Script Sandboxing Enabled in Xcode Project (from the Gradle task checkSandboxAndWriteProtection): user script sandboxing is on. Set ENABLE_USER_SCRIPT_SANDBOXING to NO for the target, run ./gradlew --stop, and rebuild (JetBrains). We reproduced this by flipping the setting back on.
  • The first iOS build takes minutes: Gradle downloads the Kotlin/Native toolchain (several hundred MB, into ~/.konan) once. Later builds are incremental.
  • "No such module 'Shared'": the script phase didn't run, or runs after Compile Sources. Check the build phase order in Xcode.
Gotcha · Swift's name for your function comes from the file name Rename Platform.ios.kt and every Swift caller of Platform_iosKt.platformName() breaks, even though no Kotlin changed. Prefer exposing classes (like Greeting) to Swift over top-level functions.

Retrieval checks

Answer from memory, without scrolling up.

Which source set may call platform.UIKit.UIDevice?

Only source sets that compile exclusively to Apple targets see the platform.* bindings.

You add a second expect fun but write only the Android actual. What happens?

The compiler checks every target: The 'expect' declaration … has no 'actual' declaration in module '<commonMain> for Native'.

What does baseName = "Shared" control?

It names the framework, so Swift writes import Shared. The Gradle module stays :shared and the package stays com.example.devicemonitor.

What does the Android app need to use Greeting?

On Android, shared is an ordinary Gradle module. The framework and build phase are the iOS mechanism.

Swift can't find a Kotlin function you wrote. Where do you look first?

The header is exactly what Swift sees, including renamed things like Platform_iosKt.

Which command catches an Android API used in commonMain fastest?

Both Android tasks compile commonMain with the Android SDK, so they accept it.

Kotlin interface is to Swift protocol as Kotlin object is to Swift:

The Objective-C header exposes a Kotlin object's single instance as shared.

iosApp/iosApp/SceneDelegate.swift 
import UIKit

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(_ scene: UIScene, willConnectTo session: UISceneSession,
               options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)
        window.rootViewController = ViewController()
        window.makeKeyAndVisible()
        self.window = window
    }
}
iosApp/iosApp/ViewController.swift 
import UIKit
import Shared

final class ViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = .systemBackground

        let label = UILabel()
        label.text = Greeting().greet()
        label.numberOfLines = 0
        label.textAlignment = .center
        label.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(label)
        NSLayoutConstraint.activate([
            label.centerYAnchor.constraint(equalTo: view.centerYAnchor),
            label.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            label.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
        ])
    }
}
