Lesson 06 · Week 2 · Day 6 · Native Device Monitor course

Declarative UI: Components, State, Layout

~2 h · +1 h per extra UI track Milestone: m01 Device Monitor screen Prereq: 05
Why this matters: every feature in the Native Device Monitor (scan results, connection state, live sensor values, permission errors) reaches the user through one screen that has to stay consistent while data arrives asynchronously. Today you build that screen's first version, milestone m01: a title with an icon, a name filter, a Scan button, a progress indicator and a status/error line. The data is a fake scan from shared Kotlin, so you can focus on how the UI reacts to it. Lesson 07 adds the device list and a second screen, and from Lesson 08 a shared ViewModel drives the screen.

Primary source Android's Thinking in Compose. It's the clearest statement of the declarative model, and everything in it applies to SwiftUI too. Read it after section 2. iOS learners add Apple's State reference page (ten minutes).

Tracks The concepts (sections 1, 2 and 6) and the shared Kotlin (section 3) are the same on every track. The screens differ per track. XML Views and UIKit are imperative toolkits. On those tracks you write the declarative discipline by hand, in a single render() function. Each excerpt below shows only the lines its notes explain, and the complete files are in Full files at the end.

1. Imperative vs declarative, by breaking one

In an imperative toolkit, widgets are objects that hold their own state, and your event handlers mutate them one call at a time: disable the button, show the spinner, set the label. In a declarative toolkit, you describe what the screen should look like for a given state, and the framework works out the changes. Android's docs put it as "conceptually regenerating the entire screen from scratch, then applying only the necessary changes" (Thinking in Compose).

The toy below is the Device Monitor's scan flow written both ways. The handlers on the left are exactly the code underneath it. Click the events in different orders until the two phones disagree. (The toy also draws the results as rows. The m01 screen shows only how many devices it found, and Lesson 07 adds the rows.)

Those two bugs are the whole argument. With n widgets and m events, imperative code has n × m places to forget an update. Declarative code has one function from state to screen. Three rules follow, and every track in this course uses them:

  
    
    
  1. UI is a function of state. The screen shows what the state says, nothing else (Thinking in Compose).
    2. 
    
  2. Single source of truth. Each piece of state lives in exactly one place. Android: "By moving state instead of duplicating it, we're ensuring there's only one source of truth" (State and Jetpack Compose). Apple: "Use state as the single source of truth for a given value type that you store in a view hierarchy" (State).
    3. 
    
  3. Derive, don't store. The status text, the button's enabled flag and the error colour are computed from isScanning and the scan result. Stored copies are how the two phones above drifted apart.
    4. 
  

  
  
From TypeScriptThis is React's model, or Angular templates with signals: the template is a function of component state, and you change state, never the DOM. Compose and SwiftUI are the same idea, with different machinery underneath: Compose relies on a Kotlin compiler plugin, SwiftUI on Swift's result builders (@ViewBuilder). XML Views and UIKit are jQuery-era: you hold references to widgets and set their properties.


  
2. Re-running the UI, and where side effects go

  
When state changes, the framework calls your UI code again. Compose calls it recomposition: "the process of calling your composable functions again when inputs change", and it "skips the rest" whose inputs didn't change. SwiftUI re-evaluates a view's body: "When the value changes, SwiftUI updates the parts of the view hierarchy that depend on the value" (Apple: State).

  
  
The consequence you must design for: your UI function runs often, and you don't control when. Composables "might be re-executed as often as every frame", children "might run in any order", and a recomposition "may be skipped" (Thinking in Compose). So the UI function must have no side effects: no starting a scan, no writing a file, no incrementing a counter. Side effects go in one of two places:

  

  

    
WhereComposeSwiftUIXML / UIKit

    
an event callback (a tap)onClick = { … }, plus rememberCoroutineScope().launch for asyncButton(action:), plus Task { } for asyncclick listener / UIAction, then call render()

    
a lifecycle-bound effect (on appear)LaunchedEffect(key).task { } / .task(id:)onCreate / viewDidLoad (viewDidLoad: Lesson 04)

  

  

  
The scan starts on a tap, so in m01 it lives in a callback. Android's guide says the same: "trigger side-effects from callbacks such as onClick that always execute on the UI thread" (same page).

  
Imperative tracks: render() is your recompositionXML Views and UIKit never re-run your code for you. So the XML and UIKit screens below keep their state in a few properties and route every change through one render() function that sets every widget from that state. It's the declarative column of the toy, written by hand. When the team's legacy screens misbehave, the cause is usually a handler that skips render() and edits one widget directly.


  
3. The data: a fake scan in shared Kotlin

  
The device list comes from commonMain, so both apps show the same devices and the filtering rule is written once. It's the first shared code the UI calls, after m00's Greeting. (Greeting.kt and Platform*.kt stay; nothing uses them now, and later lessons don't need them.)

  
  
  
    
    
  1. Device is a data class (Lesson 01), so two devices with the same fields are equal. Its id is the device's stable identity; Lesson 07 uses it as each list row's key. The fake ids look like Android MAC addresses. On iOS, a real BLE id is a UUID the system assigns, not the device's address (Lesson 13).
    2. 
    
  2. object SampleDevices is a singleton. Swift sees it as SampleDevices.shared (Lesson 05's name table), so Swift calls SampleDevices.shared.matching(filter: query). Kotlin parameter names become Swift argument labels.
    3. 
    
  3. matching is the filtering rule: a case-insensitive "contains" on the name, with the filter trimmed. An empty filter matches every device. List<Device> arrives in Swift as [Device]. The screen only needs how many matched, so Kotlin calls .size and Swift calls .count.
    4. 
    
  4. The fake scan has no delay. Waiting is the UI's job in m01. In Lesson 08 the delay moves into shared code as a Flow, and Lesson 13 replaces the fake with a real scanner.

The m01 screen uses five kinds of component, arranged in a vertical stack. Every toolkit has the same five, under different names:

  • iOS

The status line (text, with the progress indicator beside it while a scan runs) is the part that changes. Section 5 covers it. This section is the static shape.

  

  

  
  
  
  
    
    
  1. Column stacks children vertically, Arrangement.spacedBy(12.dp) spaces them, and Row does the same horizontally. Modifiers are applied in order: fillMaxSize(), then safeDrawingPadding() keeps the content out from under the system bars (with targetSdk 36 the app draws behind them, and m00's enableEdgeToEdge() makes them transparent; Lesson 05), then padding(16.dp) adds the margin.
    2. 
    
  2. Image(painterResource(R.drawable.ic_bluetooth)) draws a vector drawable from res/drawable/ (the file is in Full files, shared by both Android tracks), tinted with the theme colour. contentDescription = null marks it decorative for screen readers.
    3. 
    
  3. OutlinedTextField(value = filter, onValueChange = onFilterChange). The field displays only what state says. A keystroke is an event, the event changes state, and the new state recomposes the field. Android now recommends the newer TextFieldState API for text fields (Configure text fields). This lesson uses value + callback because it shows hoisting plainly (section 5) and matches SwiftUI's binding.
    4. 
    
  4. Button(onClick = onScan, enabled = !isScanning). enabled is the toy's buttonEnabled, derived from state. Text("Scan") is the button's content.
    5. 
    
  5. MaterialTheme { … } in MainActivity supplies the colour scheme, typography and shapes that Material components read, including MaterialTheme.colorScheme.primary on the icon. Without it they still draw, in Material's built-in light defaults; the wrapper is where an app sets its own.
    6. 
  

  

  

  
  
  
  
  
    
    
  1. ConstraintLayout. Each view pins its edges to the parent or to a sibling (layout_constraintTop_toBottomOf="@id/headerIcon"). layout_width="0dp" means "match constraints": stretch between the two anchors. The title is centred on the icon by pinning its top and bottom to the icon's. The status text sits 8dp after the progress bar (layout_marginStart). When the bar is GONE, layout_goneMarginStart="0dp" replaces that margin, so the text lines up with the field above it.
    2. 
    
  2. The FrameLayout with fitsSystemWindows="true" comes from m00. It pads everything clear of the system bars, and the 16dp padding on the ConstraintLayout inside adds the margin.
    3. 
    
  3. The icon is the same vector drawable as in Compose. app:tint="?attr/colorAccent" tints it with the theme's accent colour through AppCompat's app: attribute, and contentDescription="@null" marks it decorative.
    4. 
    
  4. ViewBinding. buildFeatures { viewBinding = true } makes Gradle generate a class from each layout file: activity_main.xml becomes ActivityMainBinding, with one typed field per view id (binding.scanButton). No findViewById, no casts. constraintlayout and lifecycle-runtime-ktx (section 5) are new dependencies.
    5. 
    
  5. AppCompat buttons render their text in capitals ("SCAN"), whatever the android:text says. UI-automation tools and tests see the capitalised text.
    6. 
  

  

  

  
XML vs Compose · what changed and whyCompose describes the layout as nested calls (Column { Row { … } }) and the framework measures them. XML says where each view sits in relation to its neighbours, in a separate file, and your Kotlin looks the views up through a generated binding.

  

  

  
  
  
  
    
    
  1. VStack(alignment: .leading, spacing: 12) stacks children vertically; HStack does it horizontally. .padding() uses the system default inset. Spacer() takes all the leftover height and pushes the content to the top. Without it the stack would sit in the middle of the screen.
    2. 
    
  2. Image(systemName:) is an SF Symbol: a vector icon built into iOS that scales with the font size. .foregroundStyle(.tint) colours it with the app's accent colour.
    3. 
    
  3. TextField(…, text: $filter). $filter is a Binding, a read-write reference to the state. The field shows filter and writes keystrokes back into it. It's Compose's value + onValueChange in one argument.
    4. 
    
  4. Button(action: scan) { Text("Scan").frame(maxWidth: .infinity) }. The frame sits on the label. Put .frame(maxWidth: .infinity) on the Button instead, and you get a small centred button in a wide invisible frame (see the gotcha in section 7).
    5. 
    
  5. .disabled(isScanning) is derived, like Compose's enabled = !isScanning.
    6. 
    
  6. The app file now shows DeviceMonitorView() directly. m00's ContentView.swift is deleted. Lesson 07 adds navigation around this view.
    7. 
  

  

  

  
  
  
  
    
    
  1. Layout: one vertical UIStackView holds the header row, the field, the button and the status row. A UIStackView arranges its arranged subviews for you, so only the outer stack needs constraints. It's pinned to the layout margins (which include the safe area) on three sides. There's no bottom constraint, so the stack is only as tall as its content and sits at the top.
    2. 
    
  2. translatesAutoresizingMaskIntoConstraints = false on the stack. Without it, UIKit adds constraints of its own that conflict with yours (Lesson 05's label did the same).
    3. 
    
  3. Content hugging. A horizontal stack with the default fill distribution has to stretch one arranged view to use the leftover width. It stretches the one with the lowest content-hugging priority, and on a tie it goes by position in arrangedSubviews. A UIImageView and a UILabel made in code both default to 250, so ours chose the icon, the first view: it stretched across the whole header row and pushed the title to the right edge (see the gotcha in section 7). setContentHuggingPriority(.required, for: .horizontal) makes the icon resist stretching, so the stack stretches the title label instead.
    4. 
    
  4. UIButton(configuration: .filled()) (declared with the widgets) is the modern button API. In a vertical stack with alignment = .fill it's as wide as the stack. UIAction { [weak self] _ in self?.scan() } avoids a retain cycle: the view controller owns the button, so the button's closure must not own the view controller.
    5. 
    
  5. The scene delegate makes this view controller the window's root. There's no navigation controller yet, so there's no navigation bar and the title is a label in the stack. Lesson 07 adds the UINavigationController. ViewController.swift (m00's greeting screen) is deleted.
    6. 
  

  

  

  
UIKit vs SwiftUI · what changed and whySwiftUI's stacks are nested values, like Compose's. UIKit's are objects you create, configure and add to a parent, then pin with constraints. In SwiftUI the filter is state bound to the field. In UIKit the text field owns it, and you read it when you need it.


  
5. State, events and the status line

  
Three pieces of state run the whole screen: the filter text, whether a scan is running, and how many devices the last scan found (null before the first scan, so the screen can tell "never scanned" from "scanned, found nothing"). On Compose, a fourth piece is the coroutine scope that runs the scan. Everything the user sees is derived from them.

  

  

  
  
    
    
  • Android
    • 
  

  
  
  
    
    
  1. var filter by rememberSaveable { mutableStateOf("") }, read inside out. mutableStateOf creates an observable value: "Any changes to value schedule recomposition of any composable functions that read value". remember keeps it across recompositions. rememberSaveable also keeps it "across activity or process recreation", such as rotation (State and Jetpack Compose). by is a Kotlin property delegate, so you write filter instead of filter.value.
    2. 
    
  2. foundCount is an Int?, with null meaning "never scanned". rememberSaveable saves any type a Bundle holds (strings, numbers, Parcelables) on its own, and an Int? is one. A Kotlin Device from shared code isn't: it would need a custom Saver. Lesson 07 needs the rows themselves and meets that limit then.
    3. 
    
  3. isScanning uses plain remember on purpose. If the Activity is recreated mid-scan, the scan coroutine is cancelled (next point). A saved true would leave the screen saying "Scanning…" forever.
    4. 
    
  4. rememberCoroutineScope() gives a scope tied to this composable's place on screen. It's cancelled when the composable leaves (rotation, navigation). That's how a callback starts async work in Compose (Side-effects in Compose). delay and launch come from kotlinx.coroutines, which arrives transitively with the Compose runtime.
    5. 
    
  5. onScan is the event handler. It changes state synchronously first (isScanning = true, result cleared), and only then launches the slow part. The button is disabled from the very next frame, so a double tap can't start two scans.
    6. 
    
  6. val query = filter captures the filter at tap time. Reading filter after the 1.5 s delay would see whatever the user typed meanwhile.
    7. 
    
  7. Stateful wrapper, stateless content. DeviceMonitorScreen owns state. DeviceMonitorContent only receives values and lambdas: "state goes down … events go up". That's state hoisting and unidirectional data flow (same page). In Lesson 08 a shared ViewModel replaces the wrapper, and DeviceMonitorContent doesn't change.
    8. 
    
  8. ScanStatus is the toy's render(): a when over state. The error is just one branch with an error colour, and the progress indicator only exists while isScanning is true.
    9. 
  

  

  

  
  
  
    
    
  1. State is two fields: foundCount and isScanning. The views are a copy of it, and render() is the only function that writes to views. That's the declarative column of the section 1 toy, by hand. binding is a lateinit field: an Activity's views live as long as the Activity does.
    2. 
    
  2. onSaveInstanceState + getInt is rememberSaveable by hand: the count survives rotation. Bundle.putInt takes a non-null Int, so the code only writes the key when there's a count, and reads it back with a default of -1. The EditText saves its own text, because it has an id.
    3. 
    
  3. scan() sets state and renders synchronously, then launches the slow part in the Activity's lifecycleScope. That scope is cancelled when the Activity is destroyed, and rotation destroys the Activity (section 6). lifecycleScope is part of the Lifecycle library, which we declare (as lifecycle-runtime-ktx) because our code uses it directly. Since Lifecycle 2.8 that -ktx artifact is empty: it pulls in lifecycle-runtime, which now holds its Kotlin APIs.
    4. 
    
  4. The query is captured at tap time: scan(binding.filterInput.text.toString()) reads the text before the delay starts.
    5. 
    
  5. The status text and its colour are derived inside render(), from the two fields, every time. Color.RED for the error is a hard-coded colour, fine for a demo.
    6. 
  

  

  

  

  

  
  
  
    
    
  1. @State private var: "SwiftUI manages the property's storage. When the value changes, SwiftUI updates the parts of the view hierarchy that depend on the value" (Apple: State). The struct itself is recreated all the time; the state isn't. Apple says to declare it private "in the highest view in the view hierarchy that needs access".
    2. 
    
  2. scan() changes state synchronously, then starts a Task for the wait. A View is @MainActor, so the Task inherits the main actor, and the writes after await happen on the main thread. It's an unstructured task (Lesson 02): leaving the screen doesn't cancel it, which is harmless on the only screen. Lesson 08 moves the scan into a ViewModel that owns its lifetime.
    3. 
    
  3. let query = filter captures the filter at tap time.
    4. 
    
  4. ScanStatus is the toy's render(), an if/else over state. foundCount: Int? uses nil for "never scanned". It takes plain values, not the state itself: the @State lives in the parent, and the parent passes values down. That's Compose's hoisting, without the lambdas, because here the parent is the only writer.
    5. 
    
  5. A View's body has no side effects. The only place the state changes is scan(), called from the button's action.
    6. 
  

  

  

  
  
  
    
    
  1. State is two properties, foundCount and isScanning. The widgets are a copy, and only render() writes to them: the declarative discipline by hand. (The filter text lives in the UITextField itself, and scan() reads it once.)
    2. 
    
  2. scan() changes state and renders synchronously, then starts a Task. UIViewController is @MainActor, so the task's code runs on the main thread after await too. Like the SwiftUI task, it isn't cancelled when the screen goes away.
    3. 
    
  3. render() sets every widget from state, every time. The spinner is started or stopped and shown or hidden; a hidden view inside a UIStackView takes no space, so the status label sits flush left when nothing is scanning.
    4. 
    
  4. The status label's colour is set on every render too: red when the count is zero, the normal label colour otherwise. Setting it only in the error branch would leave it red for the next scan, exactly the toy's bug.
    5. 
  

  

  

  
XML vs Compose · what changed and whySame state, same rules, different enforcement. Compose re-runs DeviceMonitorContent whenever state changes, so a forgotten update can't happen. In XML, nothing stops a click listener from setting statusText directly and skipping render(). The rememberSaveable line is three pieces in XML (the field, onCreate, onSaveInstanceState).

  
UIKit vs SwiftUI · what changed and whySwiftUI's @State plus a body that reads it replaces UIKit's properties, render(), and all the view setup in viewDidLoad. The scan function is nearly identical on both.


  
6. What survives what

  
"Local state" means state owned by the screen, so it dies when the screen does. We ran the m01 builds and checked what rotation does:

  

  

    
After…ComposeXMLSwiftUI / UIKit

    
rotating, result on screenfilter and result kept (saved state)filter and result kept (saved state)kept: iOS doesn't recreate screens on rotation

    
rotating during a scanthe scan is silently cancelled and the screen returns to "Tap Scan to look for devices." (the filter text stays)the scan completes

  

  

  

    Gotcha · Android forgets a running operation on rotation
    Rotation recreates the Activity (Lesson 03). That cancels the scope running the scan, and only explicitly saved values come back. For a fake scan that's an annoyance. For a BLE connection in Lesson 14 it's a dropped device. The fix isn't more saved state: move the operation out of the screen, into a ViewModel that survives configuration changes. That's Lesson 08.
  

  

    Gotcha · Compose: plain remember doesn't survive rotation
    Swap rememberSaveable for remember on the filter, and rotating the phone empties the field: remember keeps a value across recompositions, and only rememberSaveable keeps it "across activity or process recreation" (State and Jetpack Compose).

Retrieval checks

  
Answer from memory, without scrolling up.

  

    
The status line says "Devices found: 3". Where should that string live?

    

      
      
      
    

    

    
It's derived state. A stored copy is a second source of truth that can go stale, like the toy's red "Scanning…".

  

  

    
Why must a composable or a SwiftUI body never start a scan directly?

    

      
      
      
    

    

    
Recomposition / re-evaluation is frequent and can be skipped. Side effects go in callbacks or lifecycle-bound effects (LaunchedEffect, .task).

  

  

    
Compose: you rotate the phone while a scan is running. What does the screen show afterwards?

    

      
      
      
    

    

    
Rotation recreates the Activity and cancels the scan's coroutine. isScanning uses plain remember, so it starts again as false, and the result was cleared when the scan started.

  

  

    
In the XML and UIKit screens, a new Clear button should clear the result. What does its handler do?

    

      
      
      
    

    

    
Change state, then render. Editing widgets directly is exactly how the imperative phone got stuck.

  

  

    
SwiftUI: where does .frame(maxWidth: .infinity) go to make the Scan button full width?

    

      
      
      
    

    

    
The button's tappable, styled area is its label. A frame on the Button only makes a wider invisible box around a small button.

  

  

    
XML track: a view in a ConstraintLayout has layout_width="0dp". What does it mean?

    

      
      
      
    

    

    
In a ConstraintLayout, 0dp means "match constraints". The view takes the space between the anchors you gave it. wrap_content is the one that wraps.

  


  
Mixed review (interleaved)

  

    
Swift calls SampleDevices.shared.matching(filter:). What is SampleDevices in Kotlin? (Lesson 05)

    

      
      
      
    

    

    
A Kotlin object appears in Swift as its single instance, .shared.

  

  

    
A Task { } started in a SwiftUI button action runs its code after await on which actor? (Lesson 02 introduced Task and @MainActor)

    

      
      
      
    

    

    
Task { } inherits the caller's actor isolation. Task.detached doesn't.

  

  

    
What does delay(1_500) do to the thread it runs on? (Lesson 01)

    

      
      
      
    

    

    
delay is a suspending function: it parks the coroutine and resumes it later, and the thread keeps running other work, here the UI.

// Stateful: owns the screen's state and the scan side effect.
@Composable
fun DeviceMonitorScreen() {
    var filter by rememberSaveable { mutableStateOf("") }
    var foundCount by rememberSaveable { mutableStateOf<Int?>(null) }
    var isScanning by remember { mutableStateOf(false) }
    val scope = rememberCoroutineScope()

    DeviceMonitorContent(
        filter = filter,
        onFilterChange = { filter = it },
        isScanning = isScanning,
        foundCount = foundCount,
        onScan = {
            val query = filter
            isScanning = true
            foundCount = null
            scope.launch {
                delay(1_500)
                foundCount = SampleDevices.matching(query).size
                isScanning = false
            }
        },
    )
}

// Stateless: renders whatever it's given, reports events up.
@Composable
fun DeviceMonitorContent(
    filter: String,
    onFilterChange: (String) -> Unit,
    isScanning: Boolean,
    foundCount: Int?,
    onScan: () -> Unit,
) {
    Column(
        modifier = Modifier.fillMaxSize().safeDrawingPadding().padding(16.dp),
        verticalArrangement = Arrangement.spacedBy(12.dp),
    ) {
        Row(
            verticalAlignment = Alignment.CenterVertically,
            horizontalArrangement = Arrangement.spacedBy(12.dp),
        ) {
            Image(
                painter = painterResource(R.drawable.ic_bluetooth),
                contentDescription = null,
                colorFilter = ColorFilter.tint(MaterialTheme.colorScheme.primary),
                modifier = Modifier.size(32.dp),
            )
            Text("Device Monitor", style = MaterialTheme.typography.headlineSmall)
        }
        OutlinedTextField(
            value = filter,
            onValueChange = onFilterChange,
            label = { Text("Device name filter") },
            singleLine = true,
            modifier = Modifier.fillMaxWidth(),
        )
        Button(onClick = onScan, enabled = !isScanning, modifier = Modifier.fillMaxWidth()) {
            Text("Scan")
        }
        ScanStatus(isScanning = isScanning, foundCount = foundCount)
    }
}

@Composable
private fun ScanStatus(isScanning: Boolean, foundCount: Int?) {
    Row(
        verticalAlignment = Alignment.CenterVertically,
        horizontalArrangement = Arrangement.spacedBy(8.dp),
    ) {
        when {
            isScanning -> {
                CircularProgressIndicator(modifier = Modifier.size(20.dp), strokeWidth = 2.dp)
                Text("Scanning…")
            }
            foundCount == null -> Text("Tap Scan to look for devices.")
            foundCount == 0 -> Text(
                "No devices found. Try another filter.",
                color = MaterialTheme.colorScheme.error,
            )
            else -> Text("Devices found: $foundCount")
        }
    }
}

package com.example.devicemonitor.android

import android.graphics.Color
import android.os.Bundle
import android.view.View
import androidx.activity.enableEdgeToEdge
import androidx.appcompat.app.AppCompatActivity
import androidx.lifecycle.lifecycleScope
import com.example.devicemonitor.SampleDevices
import com.example.devicemonitor.android.databinding.ActivityMainBinding
import kotlinx.coroutines.delay
import kotlinx.coroutines.launch

class MainActivity : AppCompatActivity() {
    // Screen state lives in fields; render() copies it into the views.
    private var foundCount: Int? = null
    private var isScanning = false

    private lateinit var binding: ActivityMainBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        enableEdgeToEdge()
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)
        foundCount = savedInstanceState?.getInt("foundCount", -1)?.takeIf { it >= 0 }
        binding.scanButton.setOnClickListener { scan(binding.filterInput.text.toString()) }
        render()
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        foundCount?.let { outState.putInt("foundCount", it) }
    }

    private fun scan(query: String) {
        isScanning = true
        foundCount = null
        render()
        lifecycleScope.launch {
            delay(1_500)
            foundCount = SampleDevices.matching(query).size
            isScanning = false
            render()
        }
    }

    // The one place that touches views: every state change ends here.
    private fun render() {
        binding.scanButton.isEnabled = !isScanning
        binding.progress.visibility = if (isScanning) View.VISIBLE else View.GONE
        binding.statusText.text = when {
            isScanning -> "Scanning…"
            foundCount == null -> "Tap Scan to look for devices."
            foundCount == 0 -> "No devices found. Try another filter."
            else -> "Devices found: $foundCount"
        }
        binding.statusText.setTextColor(if (foundCount == 0) Color.RED else Color.DKGRAY)
    }
}

import SwiftUI
import Shared

struct DeviceMonitorView: View {
    @State private var filter = ""
    @State private var foundCount: Int? = nil
    @State private var isScanning = false

    var body: some View {
        VStack(alignment: .leading, spacing: 12) {
            HStack(spacing: 12) {
                Image(systemName: "antenna.radiowaves.left.and.right")
                    .font(.title)
                    .foregroundStyle(.tint)
                Text("Device Monitor")
                    .font(.title2)
            }
            TextField("Device name filter", text: $filter)
                .textFieldStyle(.roundedBorder)
                .autocorrectionDisabled()
            Button(action: scan) {
                Text("Scan")
                    .frame(maxWidth: .infinity)
            }
            .buttonStyle(.borderedProminent)
            .disabled(isScanning)
            ScanStatus(isScanning: isScanning, foundCount: foundCount)
            Spacer()
        }
        .padding()
    }

    private func scan() {
        let query = filter
        isScanning = true
        foundCount = nil
        Task {
            try? await Task.sleep(for: .seconds(1.5))
            foundCount = SampleDevices.shared.matching(filter: query).count
            isScanning = false
        }
    }
}

private struct ScanStatus: View {
    let isScanning: Bool
    let foundCount: Int?

    var body: some View {
        if isScanning {
            HStack {
                ProgressView()
                Text("Scanning…")
            }
        } else if let foundCount {
            if foundCount == 0 {
                Text("No devices found. Try another filter.")
                    .foregroundStyle(.red)
            } else {
                Text("Devices found: \(foundCount)")
            }
        } else {
            Text("Tap Scan to look for devices.")
        }
    }
}

import UIKit
import Shared

final class DeviceMonitorViewController: UIViewController {
    // Screen state lives in properties; render() copies it into the views.
    private var foundCount: Int? = nil
    private var isScanning = false

    private let filterField = UITextField()
    private let scanButton = UIButton(configuration: .filled())
    private let spinner = UIActivityIndicatorView(style: .medium)
    private let statusLabel = UILabel()

    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = .systemBackground

        let icon = UIImageView(image: UIImage(systemName: "antenna.radiowaves.left.and.right"))
        icon.preferredSymbolConfiguration = UIImage.SymbolConfiguration(pointSize: 28)
        icon.tintColor = .tintColor
        icon.setContentHuggingPriority(.required, for: .horizontal)
        let titleLabel = UILabel()
        titleLabel.text = "Device Monitor"
        titleLabel.font = .preferredFont(forTextStyle: .title2)
        filterField.placeholder = "Device name filter"
        filterField.borderStyle = .roundedRect
        filterField.autocorrectionType = .no
        scanButton.configuration?.title = "Scan"
        scanButton.addAction(UIAction { [weak self] _ in self?.scan() }, for: .touchUpInside)
        statusLabel.numberOfLines = 0

        let headerRow = UIStackView(arrangedSubviews: [icon, titleLabel])
        headerRow.spacing = 12
        headerRow.alignment = .center
        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let stack = UIStackView(arrangedSubviews: [headerRow, filterField, scanButton, statusRow])
        stack.axis = .vertical
        stack.alignment = .fill
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
        ])
        render()
    }

    private func scan() {
        let query = filterField.text ?? ""
        isScanning = true
        foundCount = nil
        render()
        Task {
            try? await Task.sleep(for: .seconds(1.5))
            foundCount = SampleDevices.shared.matching(filter: query).count
            isScanning = false
            render()
        }
    }

    // The one place that touches views: every state change ends here.
    private func render() {
        scanButton.isEnabled = !isScanning
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let foundCount {
            statusLabel.text = foundCount == 0
                ? "No devices found. Try another filter."
                : "Devices found: \(foundCount)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = foundCount == 0 ? .systemRed : .label
    }
}
