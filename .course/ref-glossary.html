Course Glossary

Every lesson uses these terms with exactly these meanings. Each entry names the lesson that introduces it.

Course terms

Milestone (m00…m15, e1…e3)
The finished demo state a lesson produces. Each lesson's agent brief starts from the previous milestone. (Plan)
UI track
Your choice of UI stack per platform: Android XML or Compose, iOS UIKit or SwiftUI. The default is Compose + SwiftUI. (Plan)
Agent brief
The copy-paste block at the end of each lesson that tells a coding agent what to build and how to check it. (Plan)
Unaided exercise
A small change you make without an agent. Not optional. (Plan)
Core lessons
The lessons that build the Native Device Monitor up to the finished app, sized for four 5-day weeks. (Plan)
Lesson 00
The short introduction page: what you'll build, how the course works, and the map of every lesson. Read once, in minutes, before the first lesson. (00)
Extension (course)
An optional lesson that starts from the finished core app and adds one capability (network, camera, a BLE library). (Plan)
Excerpt
The few lines of code a lesson section talks about, shown with their file path and with the rest of the file elided. Code walkthroughs are made of excerpts. (00)
Full files
The complete source of every file a lesson touches, kept collapsed at the end of the lesson so the agent brief can be built from the page alone. (00)

Language and concurrency

Data class (Kotlin)
A class for holding values; the compiler generates equals, hashCode, toString, copy. (01)
Sealed interface (Kotlin) / enum with associated values (Swift)
A closed set of cases known at compile time, so when/switch over it must be exhaustive. Used for every UI state. (01)
Extension
Adding members to an existing type without subclassing it; statically resolved. (01)
Value type / reference type
A value type (Swift struct) is copied on assignment; a reference type (class) is shared. (02)
Optional / nullable type
T?: a type that may hold no value. Must be unwrapped or given a fallback before use. (01)
Coroutine
A suspendable unit of work in Kotlin, started by a builder such as launch. (01)
Suspend function
A Kotlin function that can pause without blocking a thread; callable only from a coroutine or another suspend function. (01)
Coroutine scope / structured concurrency
A scope owns the coroutines launched in it; cancelling the scope cancels them all. (01)
Flow (cold)
An async stream whose producer runs only when collected, once per collector. (01)
StateFlow (hot, conflated)
A flow that always holds one current value; collectors see only the latest value, not a backlog. (01)
Conflation
Dropping intermediate values so a slow consumer sees only the most recent one. (01)
Backing property
Private mutable state exposed as a public read-only view (_state / state; Swift private(set)). (01)
AsyncSequence / AsyncStream (Swift)
Swift's async stream protocol and its push-based implementation (yield, finish), consumed with for await. (02)
Task (Swift)
A unit of async work. A bare Task { } is unstructured: nothing cancels it automatically. (02)
Main actor (@MainActor)
The isolation domain for UI work; code marked with it runs only there, and the compiler enforces that. (02)

Platform

Activity (Android)
An app entry point with a window and a lifecycle (onCreate … onDestroy). The course app has one. (03)
Context (Android)
Your handle to the system: resources, system services, starting components. An Activity is a Context. (03)
Intent (Android)
A message asking the OS to start something; explicit (a named class) or implicit (any app that can handle an action). (03)
Manifest / Info.plist
The declaration file each OS reads before running your code: components, permissions, metadata, permission-prompt strings. (03, 04)
Configuration change (Android)
Rotation, dark mode, font size, etc.; by default destroys and recreates the Activity. (03)
compileSdk / minSdk / targetSdk
APIs you can see / oldest Android that can install / runtime behaviour you opt into. (03)
Scene / scene phase (iOS)
One app window and its app-level state: active, inactive, background. The level to hook for "is the app in front?" (04)
View lifecycle (iOS)
Appear/disappear events for one screen inside the app (onAppear, viewWillAppear, …); not fired by backgrounding. (04)
Logger / Logcat
Apple's structured logging API (subsystem + category) / Android's log viewer for Log.d(tag, msg). (03, 04)

Kotlin Multiplatform

KMP (Kotlin Multiplatform)
Compiling one Kotlin codebase to several platforms; here the shared code of the Android and iOS apps. (05)
Shared module (:shared)
The Gradle module holding the shared Kotlin. Android depends on it as a library; iOS consumes it as a framework. (05)
Target
A platform the compiler builds for: android, iosArm64 (devices), iosSimulatorArm64 (simulator on Apple silicon). (05)
Source set
A folder of Kotlin code plus the targets it compiles to, which decides the APIs it may call: commonMain, androidMain, iosMain. (05)
Intermediate source set
A source set shared by some but not all targets, e.g. iosMain for both iOS targets. Created by Kotlin's default hierarchy. (05)
expect / actual
A declaration without a body in common code (expect) and its required per-platform implementation (actual). For small facts; behaviour goes behind a port. (05)
Kotlin/Native
The Kotlin compiler backend that produces native binaries, used for the iOS targets; exposes Apple frameworks to Kotlin as platform.*. (05)
Framework (Apple)
A bundle of a compiled binary plus headers. The shared module becomes Shared.framework, imported in Swift as import Shared. (05)
Objective-C header (Shared.h)
The generated description of the shared API that Swift actually reads; the place to look up Swift names such as Platform_iosKt. (05)
Direct integration
Wiring the framework into Xcode with a script build phase that runs :shared:embedAndSignAppleFrameworkForXcode on every build. (05)

Declarative UI

Imperative UI / declarative UI
Imperative: handlers mutate widget objects one property at a time (XML Views, UIKit). Declarative: you describe the screen for a given state and the framework applies the changes (Compose, SwiftUI). (06)
UI state
The values a screen is drawn from, e.g. isScanning and foundCount. The screen is a function of it. (06)
Single source of truth
Each piece of state lives in exactly one place; everyone else reads it or asks it to change. (06)
Derived state
A value computed from state on every render (status text, enabled flags) instead of stored. (06)
Recomposition / body re-evaluation
The framework re-running UI code when state it read changes (Compose / SwiftUI). Frequent, skippable, order not guaranteed, so UI code must be side-effect free. (06)
render()
On imperative tracks, the one function that copies all state into all widgets; every handler ends with it. (06)
Side effect
Work that changes something outside the UI function (starting a scan, writing a file). Belongs in event callbacks or lifecycle-bound effects (LaunchedEffect, .task), never in the UI function. (06)
State hoisting / unidirectional data flow
Moving state up to a caller and passing down values plus event lambdas: state goes down, events go up. A SwiftUI Binding is the two-way form. (06)
Stable key (item identity)
A unique, unchanging id per list item (the device id), used by lists to match rows across updates. Never an index. (07)
Back stack / route
The stack of screens; Back pops one. A route is the small, saveable value pushed to open a screen (DeviceDetail(id)), carrying ids, not objects. (07)
Main thread (UI thread)
The one thread allowed to touch UI. Don't block it; don't update UI from elsewhere. Swift: @MainActor. (07)

Shared ViewModels and Kotlin↔Swift

ViewModel
A screen-level state holder that outlives the screen's views: it survives Android rotation and lives until its owner is gone. AndroidX's ViewModel is multiplatform, so ours lives in commonMain. (08)
ViewModelStore / ViewModelStoreOwner
The container that keeps ViewModels, and whatever holds that container (an Activity, Fragment or navigation entry). Clearing the store clears its ViewModels. iOS has no built-in owner. (08)
ViewModelOwner (course term)
Our Swift class that plays ViewModelStoreOwner on iOS: it resolves ViewModels from a store and clears the store in deinit. (08)
Cleared (ViewModel)
The end of a ViewModel's life: onCleared() runs and viewModelScope is cancelled, which stops its work. (08)
viewModelScope
The coroutine scope of a ViewModel; everything launched in it is cancelled when the ViewModel is cleared. Runs on Dispatchers.Main.immediate. (08)
ViewModel factory
Tells the platform how to construct a ViewModel with arguments (viewModelFactory { initializer { … } }), because the platform, not your code, creates it. (08)
Lifecycle-aware collection
Collecting a flow only while the screen is visible: collectAsStateWithLifecycle, repeatOnLifecycle(STARTED), UIKit viewWillAppear/viewDidDisappear, and from Lesson 09 SwiftUI .task. Stopping collection doesn't stop the ViewModel's work. (08)
User message as state
A one-time message (an error dialog) kept in UI state until the UI reports it shown (errorShown()), instead of being sent as an event that can be lost. (08)
Impossible state
A combination of values the types allow but that means nothing (scanning with no result list). A sealed type removes it. (08)
Bridge (interop)
Code that adapts a Kotlin API into a Swift-friendly one, e.g. Lesson 08's StateFlowWatcher. Hand-written, or generated by SKIE (Lesson 09). (08)
SKIE
Touchlab's Kotlin compiler plugin that generates Swift into the framework: flows as typed AsyncSequences, sealed types via onEnum(of:), suspend as async. Pinned to exact Kotlin versions. (09)
onEnum(of:)
SKIE's function that turns a Kotlin sealed value into a generated Swift enum, so switch is exhaustive. (09)
Swift export
JetBrains' upcoming Kotlin→Swift API export (Alpha), meant to replace the Objective-C header. (09)
Sendable (Swift)
A type safe to pass between concurrency domains. Kotlin classes arrive without it, so Swift 6 rejects them in @Sendable closures. (08)
api / implementation (Gradle)
api exposes a dependency to modules that use yours; needed when its types appear in your public API (ViewModel, StateFlow). implementation keeps it private. (08)
export (framework)
Including a dependency's public API in the iOS framework header, so Swift can use its classes under clean names. (08)

Architecture, DI and testing

Hexagonal architecture / ports and adapters
Alistair Cockburn's pattern: an inside (the app core) that the outside reaches only through ports, with adapters plugged into the ports. The hexagon is just room to draw ports; six means nothing. (10)
Shared code
Everything in the shared module's commonMain: the app core plus the shared ViewModels and shared adapters. (10)
App core
The part of the shared code that holds the app's models, ports and services, and imports nothing from Android, iOS or any framework (only Kotlin's standard library and kotlinx.coroutines). Package core. (10)
Inbound port
An interface for what the app offers, one per capability (DeviceScanning), implemented by a service and called by inbound adapters and by bridge adapters. Package core.inbound. Elsewhere: driving or primary port, input boundary. (10, 17)
Outbound port
An interface for what the app needs from the outside world, named in the app's terms (BleScanner, never ApiClient), implemented by outbound adapters. Package core.outbound. Elsewhere: driven or secondary port; roughly a repository. (10)
Service
A class in the app core that implements an inbound port by applying the app's rules and calling outbound ports (ScanningService). Elsewhere, each method is roughly a use case. (10)
Inbound adapter
Code that drives the app through inbound ports: the shared ViewModels in adapter.inbound, and the tests in commonTest. (10, 11)
Outbound adapter
One concrete implementation of an outbound port for one platform or technology: the simulated scanner, an Android radio (Kotlin in androidMain), a Swift CoreBluetooth class, a Ktor HTTP client. Shared ones live in adapter.outbound. (10)
Bridge adapter (architecture; not the interop bridge)
An outbound adapter in the shared code that implements one capability's outbound port by calling another capability's inbound port (for example SessionConnectionStatus, which gives StatusService the session's connection state), so services never know each other. It holds no rules. (17)
Dependency injection (DI) / constructor injection
A class receives its dependencies (through its constructor) instead of building them. The app decides what to pass. (10)
Composition root
The one place that builds the object graph and names the services and adapters: which service backs each inbound port, which adapter backs each outbound port. AppContainer by hand (Lesson 10), then a Koin module (Lesson 11). (10, 11)
Service locator
A registry that classes ask for their dependencies (KoinComponent + get()). It hides what a class needs, so the course allows it only at the edges. (11)
DI container / Koin module
A library that builds the graph from declarations (single: one instance, factory: new each time, viewModel: new, then kept by the store). It works out the order, but with Koin's classic DSL, the one the course uses, it checks the graph only at run time. (11)
Test double
Any object a test uses in place of a real one. The course writes them by hand, as classes that implement a port, instead of using a mocking library. (11)
Fake
An outbound adapter written for tests, which the test controls (FakeBleScanner: the test decides what the radio hears and whether it fails). Android prefers fakes over mocks. A test implementation of an inbound port (TestDeviceScanning) stands in for the app core instead, so the course doesn't call it a fake. (11)
Test dispatcher / virtual time
StandardTestDispatcher queues coroutines on a test scheduler whose clock skips delays. Dispatchers.setMain puts it under viewModelScope, and runTest shares its clock. (11)
Turbine
Cash App's library for testing flows: flow.test { awaitItem() }, with a 3 s wall-clock timeout. Unconsumed items fail the test. (11)
Host test
A test that runs on the development machine's JVM (testAndroidHostTest), as opposed to a device. With the Android-KMP plugin it's off until withHostTest {}. (11)
Mutation check
Deliberately breaking one rule in production code to see whether any test fails. If none does, no test protects that rule. (11)
