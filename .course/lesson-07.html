Declarative UI: Lists, Async, Navigation

~2.5 h · +1 h per extra UI track Milestone: m02 Device Monitor shell Prereq: 06
Why this matters: a scan produces many devices, they arrive late, and the user taps one to see more. Every screen in the Native Device Monitor is some mix of those three things: a list, an update that arrives asynchronously, and a second screen. Today you finish the shell, milestone m02: m01's screen gains a list of results, with rows that keep their identity, and a detail screen you reach by tapping a row. The data is still the fake scan from shared Kotlin. From Lesson 08 a shared ViewModel drives this same screen, and from Lesson 13 a real BLE radio does.

Primary source Android's Lists and grids for keys, and Processes and threads for the main-thread rule (both are short). iOS learners add Apple's NavigationStack page.

Tracks The concepts (sections 2, 3 and 4) are the same on every track. The screens differ per track, and XML Views and UIKit keep the render() discipline from Lesson 06. Each excerpt shows only the lines its notes explain, and the complete files are in Full files at the end.

1. Results as state, and a lookup by id

A list needs the devices themselves, so the state changes from a count to the results: a list that is null before the first scan (so the screen can still tell "never scanned" from "scanned, found nothing") and possibly empty afterwards. The status line is still derived from it: "Devices found: N" is the list's size.

Shared Kotlin gets one new function, find(id). It returns the device with that id, or null. Two places use it below: Compose needs it to rebuild the rows from saved ids, and the detail screen needs it to show a device from nothing but its id.

Swift calls it as SampleDevices.shared.find(id: deviceId). It returns Device?, which Swift sees as an optional, so Swift code unwraps it with if let.

  1. The state holds ids, not devices. rememberSaveable saves the types a Bundle can hold: strings, numbers, Parcelables. A list of id strings qualifies, and our build kept it across rotation. A Kotlin Device from shared code isn't one of those types, and saving it would need a custom Saver.
  2. devices is derived on every recomposition: find turns each saved id back into its device. The ids are the single source of truth, and the rows are computed from them, as the status line was in m01.
  3. onScan is m01's handler with ids in place of a count: it clears the results synchronously (foundIds = null), then waits, then stores the ids of the matches. val query = filter still captures the filter at tap time.
  4. onDeviceClick is a new event, passed up unchanged. The list screen reports "this device was tapped" and doesn't know what happens next. Section 4 shows who decides.
  5. The stateful wrapper and the stateless content are still two functions (DeviceListScreen and DeviceListContent), the same split as DeviceMonitorScreen and DeviceMonitorContent in m01. In Lesson 08 a shared ViewModel replaces the wrapper, and the content function doesn't change.
  1. State is two fields: foundIds and isScanning. The views are a copy of it, and render() is the only function that writes to views, as in m01. The state now holds the ids of the found devices rather than a count.
  2. onSaveInstanceState + getStringArrayList is rememberSaveable by hand: the results survive rotation as a list of ids. The EditText saves its own text, because it has an id. A Bundle holds strings, not our Device, so render() turns the ids back into devices with find.
  3. scan() sets state and renders synchronously, then launches the slow part in the Fragment's lifecycleScope. That scope lives as long as the Fragment, not its views. So a scan started before you open the detail screen finishes while you're there, and its results show when you return. Rotation destroys the Fragment and cancels the scan (section 5).
  4. binding is nullable. A Fragment outlives its views: when you navigate to the detail screen, the Fragment stays on the back stack but onDestroyView runs. render() returns early when there is no view. When you come back, onCreateView builds fresh views and calls render(), so they show the current state.
  5. The last line of render() hands the derived list to the adapter. Section 2 covers what the adapter does with it.

XML vs Compose · what changed and whySame state, same rules, different enforcement. Compose re-runs DeviceListContent whenever state changes, so a forgotten update can't happen. In XML, nothing stops a click listener from setting statusText directly and skipping render(). The rememberSaveable line is three methods in XML (onCreate, onSaveInstanceState, the field). The Fragment also needs the nullable-binding dance, because its views die before it does.

  1. The state holds the devices themselves. devices: [Device]? uses nil for "never scanned". Unlike Android's saved state, @State isn't squeezed through a Bundle, so nothing needs converting to ids.
  2. scan() changes state synchronously, then starts a Task for the wait. A View is @MainActor, so the Task inherits the main actor, and the writes after await happen on the main thread (section 3). It's an unstructured task (Lesson 02): leaving the screen doesn't cancel it. That's harmless here, because the list is the root screen. Lesson 08 moves the scan into a ViewModel that owns its lifetime.
  3. ScanStatus is m01's status view with devices in place of foundCount: an if/else over state. The count is devices.count, derived each time.
  1. State is two properties, devices and isScanning. The widgets are a copy, and only render() writes to them: the declarative discipline by hand, as in m01. (The filter text lives in the UITextField itself, and scan() reads it once.) devices replaces m01's foundCount, and nil still means "never scanned".
  2. scan() changes state and renders synchronously, then starts a Task. UIViewController is @MainActor, so the task's code runs on the main thread after await too (section 3).
  3. render() sets every widget from state, every time. The table's contents are set the same way, from a snapshot (section 2).

UIKit vs SwiftUI · what changed and whySwiftUI's @State plus a body that reads it replaces UIKit's properties, render(), and all the view setup in viewDidLoad. The scan function is nearly identical on both. One real difference: in SwiftUI the filter is state (bound to the field), while in UIKit the text field owns it and you read it when you need it.

2. Lists need stable keys

A list widget reuses row views and animates insertions, moves and removals. To do that, it must know which row is which across updates, and position isn't enough. By default Compose keys each item "against the position of the item", so "items which change position effectively lose any remembered state". Giving each item "a stable and unique key" fixes it (Lists and grids). Every track uses the device's id.

From TypeScriptThis is React's key prop on list items, or Angular's track item.id in an @for block. React warns you when you skip it. Compose, if you skip it, silently falls back to the position, and the bug shows up only when items change position: an insert, a removal (a new filter) or a reorder.

  2. items(list, key = { it.id }) is the key. devices.orEmpty() turns the null of "never scanned" into an empty list, so the list shows nothing and the status line explains why.
  3. ListItem is Material 3's row with headline, supporting and trailing slots, and Modifier.clickable turns the whole row into a tap target.

  2. DeviceDiff answers two questions: same item (same id)? Same contents (data-class equality)? The first is the key. The second decides whether a row needs re-binding.
  3. ViewHolder holds one row's binding. onCreateViewHolder inflates a row (rarely: rows are recycled). onBindViewHolder fills a recycled row with the device at that position, every time a row scrolls into view.
  4. The layout manager is set in the layout XML (app:layoutManager). A RecyclerView without one shows nothing. The row dividers come from the DividerItemDecoration added in onCreateView; RecyclerView draws none by default.
  5. adapter = null in onDestroyView (in the full file). The adapter is a Fragment field. When a RecyclerView is given an adapter, it registers itself as the adapter's observer. Without this line, the Fragment on the back stack would keep the destroyed list alive through the adapter.
  1. List(devices ?? [], id: \.id) is the key. \.id is a key path to each device's id. Device comes from Kotlin and doesn't conform to Identifiable, so the key path is passed explicitly.
  2. devices ?? [] turns the nil of "never scanned" into an empty list.
  3. Each row is a NavigationLink (section 4), which adds the disclosure chevron. DeviceRow is a plain view: an HStack with a two-line VStack, a Spacer and the signal.
  1. UITableViewDiffableDataSource<Int, String>: section identifiers are Ints (one section, 0), and item identifiers are device id Strings, so the key is the item. The closure builds a cell for an id (Apple: UITableViewDiffableDataSource).
  2. In render(), you build a fresh NSDiffableDataSourceSnapshot from state and apply it. UIKit diffs the snapshots and animates the changes. That's the declarative idea inside an imperative toolkit.
  3. UIListContentConfiguration.subtitleCell() is the standard two-line cell. dequeueReusableCell recycles cells, like RecyclerView's ViewHolders.
  4. lazy var: the data source needs tableView, so it's created on first use, after the properties exist.

3. Async updates and the main-thread rule

Every UI toolkit here is single-threaded. Android's two rules are "Don't block the UI thread" and "Don't access the Android UI toolkit from outside the UI thread", because "the Android UI toolkit is not thread-safe" (Processes and threads). On iOS, UIViewController and SwiftUI's View are @MainActor, and the Swift 6 compiler checks it (Lesson 02). The scan you wrote in section 1 follows both rules: delay and Task.sleep suspend without blocking a thread, and the state updates after them run on the main thread.

To see what each toolkit does when you break the second rule, we moved the post-scan update onto a background thread on each track:

TrackWhat we changedWhat happened
ComposewithContext(Dispatchers.Default) { foundIds = … }No crash. The list updated (the write ran on DefaultDispatcher-worker-1). Compose state tolerates it, but don't build on that: Lesson 08's shared ViewModel publishes UI state on the main thread.
XMLwithContext(Dispatchers.Default) { render() }Crash: CalledFromWrongThreadException: Only the original thread that created a view hierarchy can touch its views. Expected: main Calling: DefaultDispatcher-worker-1
SwiftUITask.detached { devices = … }Compiler warning (Swift 6 mode): main actor-isolated property 'devices' can not be mutated from a nonisolated context. It's only a warning because the view gets its main-actor isolation from View, which SwiftUI declares @preconcurrency: a home-made property wrapper in the same place gets the same warning, and in a struct marked @MainActor directly the same write is an error. This course treats warnings as errors.
UIKitTask.detached { self.render() }Compiler error: main actor-isolated instance method 'render()' cannot be called from outside of the actor

The rule to carry forward: do slow work off the main thread, and publish UI state on it. In the BLE lessons, radio callbacks can arrive on threads other than the main one, and they must be back on the main thread before the UI sees them. From Lesson 08 that's the shared ViewModel's job: it publishes UI state on the main thread, whatever thread the data came from.

From TypeScriptThe browser has one UI thread too, and await doesn't block it, exactly like delay and Task.sleep here. What differs is how easy it is to leave that thread. A web page's JavaScript has no other thread that can touch the page (a Worker can't reach the DOM), while on Android and iOS another thread is one call away (Dispatchers.Default, Task.detached) and can reach UI objects. That is why these platforms have a written rule, and why Swift 6 enforces it in the compiler.

4. A second screen: navigation as a back stack

Every navigation system here is a back stack: the root screen at the bottom, pushed screens on top, Back pops one. Two ideas carry across tracks:

  • A route is a value. You navigate by pushing a small value that describes the destination (DeviceDetail(id), DeviceRoute(id:), a Bundle with deviceId), and the system maps it to a screen.
  • Pass the id, not the object. Android must be able to save the route (process death, rotation), so routes hold small saveable values. The detail screen then looks the device up from the single source of truth (SampleDevices.find). The detail screen's only state is deviceId, and everything it displays is derived from it.

From TypeScriptThe back stack is the browser's history stack, and a route is a URL with parameters, like /devices/:id. The detail screen reads :id and looks the device up, as a web page would.

  1. Routes are @Serializable types: an object for a screen without arguments, a data class for one with arguments. That needs the Kotlin serialization plugin (same version as Kotlin) and kotlinx-serialization-core (Navigation setup, type safety). We declare the serialization library ourselves because our code uses @Serializable directly.
  2. NavHost(navController, startDestination = DeviceList) is the back stack's container. composable<DeviceDetail> { entry -> … } maps a route type to a screen, and entry.toRoute() gives back the typed route with its id.
  3. navController.navigate(DeviceDetail(device.id)) pushes. The list screen doesn't know about the NavController: it only reports onDeviceClick (events up). The app composable decides what a click means.
  4. Scaffold supplies innerPadding for the system bars, and Modifier.padding(innerPadding) keeps both screens out from under them. m01's screen did this itself with safeDrawingPadding().
  5. dropUnlessResumed { onBack() } ignores the tap unless the screen is fully resumed. Without it, a fast double tap on Back popped twice and left a blank screen (section 6). System Back (gesture or button) is handled by NavHost itself.
  6. The detail screen has no state of its own: it derives everything from deviceId. If the id is unknown, it shows an error instead of crashing. The Bluetooth icon is m01's header icon, now on this screen (the file res/drawable/ic_bluetooth.xml doesn't change).
Navigation Compose vs Navigation 3 Google also ships Navigation 3 (stable). In Nav3 the back stack is a list you own: you add and remove keys yourself, which is exactly SwiftUI's NavigationStack(path:) model (Navigation 3). Google's main navigation guide still says "If your app is built entirely with Jetpack Compose, use Navigation Compose" (Navigation), so this course uses Navigation Compose. The concepts (routes as values, ids not objects, one back stack) carry over unchanged.
  1. One Activity, many Fragments. MainActivity now only sets a layout holding a FragmentContainerView whose class is NavHostFragment. The NavHostFragment reads nav_graph.xml and swaps Fragments in and out. defaultNavHost="true" lets it handle the system Back button. m01's MainActivity held the whole screen and its render(); that code now lives in DeviceListFragment.
  2. The nav graph lists destinations (each a Fragment class), the startDestination, an action (toDetail) and the detail's typed argument. If you've seen this file in the team's app: only the start destination appears on launch, and every other screen is reached by navigate().
  3. navigate(R.id.toDetail, Bundle().apply { putString("deviceId", device.id) }) pushes, passing the id in a Bundle. requireArguments().getString("deviceId") reads it on the other side. The shorter bundleOf("deviceId" to device.id) is deprecated in core-ktx 1.19.1 ("does not provide type safety at compile time") and gives a compiler warning. The Safe Args Gradle plugin generates typed wrappers for arguments; it isn't needed for one.
  4. The FrameLayout wrapper with fitsSystemWindows="true" pads everything clear of the system bars. Putting fitsSystemWindows on the FragmentContainerView itself did nothing in our build: the list drew under the status bar (section 6).
  5. The detail Fragment has no state of its own: it reads its argument and fills its views once. A Fragment's argument Bundle is saved and restored for you, so rotation needs no extra code here. (The Bluetooth icon in fragment_device_detail.xml is m01's header icon, tinted through AppCompat's app:tint.)
  6. Both Back paths are guarded. The row click navigates only while the list is the current destination, and Back pops only while the detail is. Without the checks, two fast taps navigated or popped twice (section 6).

XML vs Compose · what changed and whyNavigation Compose keeps the graph in Kotlin (composable<Route>), with typed routes checked by the compiler. The Fragment version keeps it in XML, with string-keyed Bundle arguments checked at runtime. Both keep a back stack inside one Activity. The Fragment version's extra layer (Fragment lifecycle plus view lifecycle) is why binding is nullable there and why the adapter needs clearing.

  1. NavigationStack { root } owns the back stack. NavigationLink(value: DeviceRoute(id: device.id)) in the list pushes a value, and .navigationDestination(for: DeviceRoute.self) maps that value type to a screen. Apple's docs describe exactly this pairing (Apple: NavigationStack).
  2. DeviceRoute is a Hashable struct, the Swift twin of Compose's DeviceDetail(id). Pushing a bare String would work too. A named type keeps destinations from colliding once a second screen also takes a String.
  3. .navigationDestination goes inside the stack, on the root view, not on the NavigationStack itself.
  4. For programmatic navigation (deep links, "go back to root"), use NavigationStack(path: $path) with an array you own. "The stack adds items to the collection as it adds views to the stack and removes items when it removes views" (same page). We don't need it yet.
  5. The detail view has no state of its own: deviceId is all it holds, and everything it shows comes from find. Image(systemName:) (in the full file) is the same SF Symbol as m01's header icon.
  6. The back button and swipe-back come with the NavigationStack, so no code is needed. .navigationBarTitleDisplayMode(.inline) keeps the detail screen's title small. The list's .navigationTitle("Device Monitor") is the screen's title now, in place of m01's header row. iOSApp.swift shows ContentView() again, as in m00.
  1. UINavigationController(rootViewController:) is the back stack. It provides the navigation bar, the back button and swipe-back. The scene's root is now the navigation controller, not the screen itself as in m01.
  2. pushViewController(_:animated:) (in the list's didSelectRowAt) pushes a new DeviceDetailViewController(deviceId:). In UIKit, the "route" is the initializer's parameter list.
  3. required init?(coder:) is needed because we add our own initializer. It would only be called when loading from a storyboard, which this app doesn't use.
  4. dataSource.itemIdentifier(for: indexPath) turns a tapped row back into its id. The id travels, not the Device.
  5. The title and the large title come from the navigation controller: title plus prefersLargeTitles on the list, and largeTitleDisplayMode = .never on the detail. They replace m01's header row.
  6. AppDelegate.swift and project.yml stay as in m00. The detail screen builds the same SF Symbol icon as m01's header (see the full file).

UIKit vs SwiftUI · what changed and whyIn UIKit you push view controller instances, so the call site decides which screen opens. In SwiftUI you push values, and the stack decides which screen a value means. That's why SwiftUI can restore or rewrite the whole stack from an array, and UIKit can't without extra code.

5. What survives what

"Local state" means state owned by the screen, so it dies when the screen does. Now that there are two screens, there's a new case: leaving the list and coming back. We ran the m02 builds and checked it, next to the rotation cases from Lesson 06:

Gotcha · Compose: remember forgets when you navigate away Swap rememberSaveable for remember on the results, open a device, come back: the results are gone. We reproduced this. NavHost removes the list screen from composition while the detail is shown, and only saved state is restored. SwiftUI's root view, by contrast, stays alive under the pushed screen.
Gotcha · SwiftUI: .task and onAppear run again when you come back We logged a .task on the list view. It ran at launch and again after popping back from the detail screen, while the @State was untouched. Don't start a scan in .task or onAppear unless you want it on every return. This is the view lifecycle from Lesson 04 at work.

6. What actually happens

We built m02 with the brief below (Kotlin 2.4.21, AGP 9.4.1, Compose BOM 2026.09.00, Navigation 2.10.2, Xcode 26.2) and ran it on the Android 16 emulator and the iOS 26.2 simulator. Tap Scan: the button greys out and "Scanning…" shows with a spinner for 1.5 s. Then "Devices found: 5" and five rows, strongest signal first. A filter of sens finds one device, and zzz shows the red error. Tapping a row opens the detail screen, and Back returns to the list with the results still there.

m02 is a natural stop. It's done when both apps build and the shell behaves as above. Commit it before the next lesson, which starts from this state.

Gotcha · Android: a fast double tap navigates twice
  • Compose: with onClick = { navController.popBackStack() }, two fast taps on our Back button popped the detail screen and then the list, leaving an empty NavHost and a blank app. dropUnlessResumed { … } (from lifecycle-runtime-compose) fixed it. Inside a NavHost destination, the lifecycle it checks is the detail screen's back-stack entry, which stops being resumed as soon as the first tap pops it, so the second tap is dropped.
  • Fragments, worse because it's hidden: two truly simultaneous taps on an unguarded Back left the list on screen but popped its back-stack entry too. The next row tap crashed with IllegalArgumentException: Navigation action/destination …:id/toDetail cannot be found from the current destination. An unguarded double tap on a row crashed immediately, the same way. Checking currentDestination?.id before navigate/popBackStack fixed both. Tapping slowly by hand, or through one adb session, never showed the problem. It took two parallel adb sessions.
Gotcha · XML: fitsSystemWindows on the wrong view android:fitsSystemWindows="true" on the FragmentContainerView was ignored, and the title drew under the status bar. Wrapping it in a FrameLayout that has the attribute fixed it.

Retrieval checks

Answer from memory, without scrolling up.

What should a device list use as each row's key?

Positions change on every filter or sort, and two devices can share a name. The id follows the device.

XML track: render() runs inside withContext(Dispatchers.Default). What happens?

CalledFromWrongThreadException at runtime. The Kotlin compiler doesn't know about Android's thread rule. Swift's compiler does know about @MainActor.

Why does the detail route carry only the device id?

The back stack is saved and restored, so routes hold saveable values. The screen then derives the rest from the single source of truth.

Compose: you open a device and press Back. Which keeps the scan results on the list screen?

NavHost removes the list screen from composition while the detail is on top. Plain remember is dropped with it, and only saved state is restored.

SwiftUI: the list view has .task { scan() }. When does a scan start?

The view's .task runs each time the view appears, and the list appears again when the detail is popped. Start a scan from the button's action instead.

Mixed review (interleaved)

XML or UIKit: a click handler sets statusText directly and never calls render(). What goes wrong? (Lesson 06)

Only render() makes every widget match the state. A direct edit is how the imperative phone in Lesson 06's toy got stuck.

Swift calls SampleDevices.shared.find(id:). What is SampleDevices in Kotlin? (Lesson 05)

A Kotlin object appears in Swift as its single instance, .shared.

A Task { } started in a SwiftUI button action runs its code after await on which actor? (Lesson 02 introduced Task and @MainActor)

Task { } inherits the caller's actor isolation. Task.detached doesn't, which is what section 3's experiment exploited.

Android: you rotate the phone while a scan is running in a coroutine scope tied to the screen. What happens to the scan? (Lesson 03)

Rotation recreates the Activity, and the scope tied to the old screen is cancelled with it. Lesson 08 moves the scan out of the screen.

object SampleDevices {
    val all: List<Device> = listOf(

        Device(id = "C4:7C:8D:6A:01:11", name = "Heart Rate Monitor", rssi = -61),

// Stateful: owns the screen's state and the scan side effect.
@Composable
fun DeviceListScreen(onDeviceClick: (Device) -> Unit) {
    var filter by rememberSaveable { mutableStateOf("") }
    var foundIds by rememberSaveable { mutableStateOf<List<String>?>(null) }
    var isScanning by remember { mutableStateOf(false) }
    val scope = rememberCoroutineScope()

    DeviceListContent(
        filter = filter,
        onFilterChange = { filter = it },
        isScanning = isScanning,
        devices = foundIds?.mapNotNull { SampleDevices.find(it) },
        onScan = {
            val query = filter
            isScanning = true
            foundIds = null
            scope.launch {
                delay(1_500)
                foundIds = SampleDevices.matching(query).map { it.id }
                isScanning = false
            }
        },
        onDeviceClick = onDeviceClick,
    )
}

// Stateless: renders whatever it's given, reports events up.
@Composable
fun DeviceListContent(
    filter: String,
    onFilterChange: (String) -> Unit,
    isScanning: Boolean,
    devices: List<Device>?,
    onScan: () -> Unit,
    onDeviceClick: (Device) -> Unit,
) {
    Column(
        modifier = Modifier.fillMaxSize().padding(16.dp),
        verticalArrangement = Arrangement.spacedBy(12.dp),
    ) {
        Text("Device Monitor", style = MaterialTheme.typography.headlineSmall)
        OutlinedTextField(
            value = filter,
            onValueChange = onFilterChange,
            label = { Text("Device name filter") },
            singleLine = true,
            modifier = Modifier.fillMaxWidth(),
        )
        Button(onClick = onScan, enabled = !isScanning, modifier = Modifier.fillMaxWidth()) {
            Text("Scan")
        }
        ScanStatus(isScanning = isScanning, devices = devices)
        LazyColumn(modifier = Modifier.weight(1f)) {
            items(devices.orEmpty(), key = { it.id }) { device ->
                DeviceRow(device = device, onClick = { onDeviceClick(device) })
                HorizontalDivider()
            }
        }
    }
}

@Composable
private fun ScanStatus(isScanning: Boolean, devices: List<Device>?) {
    Row(
        verticalAlignment = Alignment.CenterVertically,
        horizontalArrangement = Arrangement.spacedBy(8.dp),
    ) {
        when {
            isScanning -> {
                CircularProgressIndicator(modifier = Modifier.size(20.dp), strokeWidth = 2.dp)
                Text("Scanning…")
            }
            devices == null -> Text("Tap Scan to look for devices.")
            devices.isEmpty() -> Text(
                "No devices found. Try another filter.",
                color = MaterialTheme.colorScheme.error,
            )
            else -> Text("Devices found: ${devices.size}")
        }
    }
}

@Composable
private fun DeviceRow(device: Device, onClick: () -> Unit) {
    ListItem(
        headlineContent = { Text(device.name) },
        supportingContent = { Text(device.id) },
        trailingContent = { Text("${device.rssi} dBm") },
        modifier = Modifier.clickable(onClick = onClick),
    )
}

import android.graphics.Color

import androidx.fragment.app.Fragment
import androidx.lifecycle.lifecycleScope

import androidx.recyclerview.widget.DividerItemDecoration
import com.example.devicemonitor.SampleDevices
import com.example.devicemonitor.android.databinding.FragmentDeviceListBinding
import kotlinx.coroutines.delay
import kotlinx.coroutines.launch

class DeviceListFragment : Fragment() {
    // Screen state lives in fields; render() copies it into the views.
    private var foundIds: ArrayList<String>? = null
    private var isScanning = false

    private var binding: FragmentDeviceListBinding? = null
    private val adapter = DeviceAdapter { device ->
        val nav = findNavController()
        // A fast double tap delivers two clicks; only navigate from the list itself.
        if (nav.currentDestination?.id == R.id.deviceList) {
            nav.navigate(R.id.toDetail, Bundle().apply { putString("deviceId", device.id) })
        }
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        foundIds = savedInstanceState?.getStringArrayList("foundIds")
    }

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        val b = FragmentDeviceListBinding.inflate(inflater, container, false)
        binding = b
        b.deviceList.adapter = adapter
        b.deviceList.addItemDecoration(DividerItemDecoration(requireContext(), DividerItemDecoration.VERTICAL))
        b.scanButton.setOnClickListener { scan(b.filterInput.text.toString()) }
        render()
        return b.root
    }

    override fun onDestroyView() {
        super.onDestroyView()
        binding?.deviceList?.adapter = null // the adapter outlives the view; don't let it keep the old list
        binding = null
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        outState.putStringArrayList("foundIds", foundIds)
    }

    private fun scan(query: String) {
        isScanning = true
        foundIds = null
        render()
        lifecycleScope.launch {
            delay(1_500)
            foundIds = ArrayList(SampleDevices.matching(query).map { it.id })
            isScanning = false
            render()
        }
    }

    // The one place that touches views: every state change ends here.
    private fun render() {
        val b = binding ?: return
        val devices = foundIds?.mapNotNull { SampleDevices.find(it) }
        b.scanButton.isEnabled = !isScanning
        b.progress.visibility = if (isScanning) View.VISIBLE else View.GONE
        b.statusText.text = when {
            isScanning -> "Scanning…"
            devices == null -> "Tap Scan to look for devices."
            devices.isEmpty() -> "No devices found. Try another filter."
            else -> "Devices found: ${devices.size}"
        }
        b.statusText.setTextColor(if (devices?.isEmpty() == true) Color.RED else Color.DKGRAY)
        adapter.submitList(devices.orEmpty())
    }
}

import UIKit
import Shared

final class DeviceListViewController: UIViewController, UITableViewDelegate {
    // Screen state lives in properties; render() copies it into the views.
    private var devices: [Device]? = nil
    private var isScanning = false

    private let filterField = UITextField()
    private let scanButton = UIButton(configuration: .filled())
    private let spinner = UIActivityIndicatorView(style: .medium)
    private let statusLabel = UILabel()
    private let tableView = UITableView()
    private lazy var dataSource = UITableViewDiffableDataSource<Int, String>(tableView: tableView) {
        tableView, indexPath, deviceId in
        let cell = tableView.dequeueReusableCell(withIdentifier: "device", for: indexPath)
        var content = UIListContentConfiguration.subtitleCell()
        if let device = SampleDevices.shared.find(id: deviceId) {
            content.text = device.name
            content.secondaryText = "\(device.id)   \(device.rssi) dBm"
        }
        cell.contentConfiguration = content
        cell.accessoryType = .disclosureIndicator
        return cell
    }

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "Device Monitor"
        navigationController?.navigationBar.prefersLargeTitles = true
        view.backgroundColor = .systemBackground

        filterField.placeholder = "Device name filter"
        filterField.borderStyle = .roundedRect
        filterField.autocorrectionType = .no
        scanButton.configuration?.title = "Scan"
        scanButton.addAction(UIAction { [weak self] _ in self?.scan() }, for: .touchUpInside)
        statusLabel.numberOfLines = 0
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "device")
        tableView.delegate = self

        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let stack = UIStackView(arrangedSubviews: [filterField, scanButton, statusRow, tableView])
        stack.axis = .vertical
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
            stack.bottomAnchor.constraint(equalTo: view.bottomAnchor),
        ])
        render()
    }

    private func scan() {
        let query = filterField.text ?? ""
        isScanning = true
        devices = nil
        render()
        Task {
            try? await Task.sleep(for: .seconds(1.5))
            devices = SampleDevices.shared.matching(filter: query)
            isScanning = false
            render()
        }
    }

    // The one place that touches views: every state change ends here.
    private func render() {
        scanButton.isEnabled = !isScanning
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let devices {
            statusLabel.text = devices.isEmpty
                ? "No devices found. Try another filter."
                : "Devices found: \(devices.count)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = devices?.isEmpty == true ? .systemRed : .label

        var snapshot = NSDiffableDataSourceSnapshot<Int, String>()
        snapshot.appendSections([0])
        snapshot.appendItems((devices ?? []).map(\.id))
        dataSource.apply(snapshot, animatingDifferences: true)
    }

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        guard let deviceId = dataSource.itemIdentifier(for: indexPath) else { return }
        navigationController?.pushViewController(DeviceDetailViewController(deviceId: deviceId), animated: true)
    }
}
